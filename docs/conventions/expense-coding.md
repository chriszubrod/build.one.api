- **Expense coding cockpit (U-005, 2026-07-14) — the ONLY sanctioned app→QBO expense write.** Card spend lands in QBO as Purchases auto-coded to the placeholder GL account `Cost of construction : NEED TO CATEGORIZE` (58999). `entities/coding_suggestion/` is the coding **queue + trust-gate + metric store** (`dbo.CodingSuggestion` — ⚠️ was `entities/expense_coding_item/` / `dbo.ExpenseCodingItem` until U-652 migrated both; that entity dir now holds only `__init__.py`, one row per target 58999 line, **seeded lazily on queue read** — the queue itself (`ReadExpenseCodingQueue`, `purchase/sql/qbo.expense_coding_queue.sql`) reads `qbo.PurchaseLine` staging directly, so a 58999 line is queue-visible the moment the purchase tick stages it; `ReadExpenseCodingQueue` surfaces the Ramp `PrivateNote` + `Credit` + `SyncToken`; router gated `Modules.EXPENSES`: queue/metrics/claim/flag/**confirm**/suggest). A **deterministic** suggestion engine (`business/suggestion_service.py` behind the pure `hint_extractor.py` seam — abbrev-exact + `FindProjectForInvoice` + `FindSubCostCodeForReply` + a NEW vendor→dominant-SubCostCode history) fills `{Project, SubCostCode, Description}` + reason + confidence, or flags "needs cardholder follow-up"; a `SubCostCode` with no `ItemSubCostCode` mapping is dropped (never suggest an unwritable coding). On human confirm, a **purpose-built single-line SURGICAL recode** — `PurchaseExpenseConnector.recode_purchase_line` — round-trips the **RAW** QBO Purchase JSON (`get_purchase_raw` → mutate ONLY the target line dict → `update_purchase_raw`) so every sibling line + its QBO line Id + all header fields stay byte-identical and the amount is untouched. **Do NOT reuse the dormant `sync_to_qbo_purchase`** (it rebuilds all lines from local data and silently drops any lacking a SubCostCode→Item mapping → sibling loss — verified P0). **Fail-closed on SyncToken**: the outbox handler `_handle_recode_purchase_line` catches `PurchaseChangedInQboError`/`QboSyncTokenMismatchError` → marks the item `changed_in_qbo` (re-review), it must NEVER reach the worker's generic refresh-and-retry (which would clobber a concurrent QBO/Ramp edit and doesn't support this entity_type). The recode write is **double-gated**: it enqueues only when BOTH `ALLOW_QBO_WRITES` AND `ALLOW_EXPENSE_RECODE_WRITES` (default off) are true — both checked **at the top of `confirm()`** (U-058a, supersedes the U-005 Phase-F record-on-gate-off criterion): with either gate off, confirm **rejects HTTP 422** (plain-string `detail` = `"qbo_writes_disabled"` / `"recode_writes_disabled"`) with **zero DB writes** — never a recorded-but-unenqueued `'confirmed'` (the 2026-07-16 trap: 44 codings looked confirmed but never reached QBO; recovered by manual outbox backfill). Contract for the web cockpit: `GET /expense-coding/metrics` exposes `recode_writes_enabled` (the AND of both gates); a confirm `200` always carries `enqueued: true`. ⛔ **Gate-P2 precondition before real-volume writes:** one controlled live recode + re-pull + a live fail-closed test (no sandbox realm wired as of build). - **Row access for a CodingSuggestion (U-652e → U-652d4 → U-652d7).** One gate, `CodingSuggestionService.assert_accessible`, called by flag, confirm (router and again under the lock) and suggestion persistence. A refused row is the same 404 as a missing one. The scope is the first of these that applies:
  1. The suggestion's Expense, via `UserCanAccessExpense`.
  2. Its project (confirmed, otherwise suggested), via `UserCanAccessProject`.
  3. **Neither**: system admin or system context only (`shared/access.py::assert_admin_or_system_context`). Chris decided this on 2026-11-14; before it, these rows were open to any EXPENSES `can_update` holder.

  **The read side uses the same rule (U-652d8).** `ReadExpenseCodingQueue` and both `ReadExpenseCodingMetrics` scans apply it, with `CodingSuggestion.ExpenseId` as the expense. A line with no suggestion row yet (nothing to write to) is scoped by its purchase's `dbo.Expense`, matched by QBO identity, so it stays visible to whoever can see that expense. A seeded row never takes that fallback, so read and write agree exactly. Before this, every EXPENSES reader saw 391–394 of the 394 queue rows. Pinned by `tests/test_u652d8_queue_access_predicate.py`, which evaluates the predicate lifted from the SQL.
- **Where a CodingSuggestion row comes from (U-652d10).** The QBO purchase pull creates it: every `QboPurchaseService.sync_from_qbo` run (empty ticks included, after the delete reconcile) calls `CodingSuggestionService.seed_unseeded_purchases`, which reads `ReadUnseededCodingPurchases` (a purchase with ≥1 `IsUncodedPlaceholder` line and no row for its RealmId + QboPurchaseQboId; oldest first, 200 per call) and upserts each with the idempotent U-652a MERGE. It scans the whole realm, not just what the pull fetched, so a failed seed retries next tick. It is DB-local, so the recode write gate does not apply; a failure is logged by class name and never fails the pull. A purchase seeded before its Expense exists gets a NULL ExpenseId until the stranded sweep's `heal_expense_ids` stamps it, and is admin-only until then. **`get_expense_coding_queue` no longer writes** (it used to seed on read). Expense review submit still seeds its own purchase (`ensure_for_expense`, gated) as a second path. Pinned by `tests/test_u652d10_seed_at_pull.py`.

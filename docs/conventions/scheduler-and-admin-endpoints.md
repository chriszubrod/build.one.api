## Scheduler Architecture (April 2026)

Recurring jobs (outbox drain, QBO pulls, daily reconciles) live in the sibling `build.one.scheduler` repo — an Azure Function App (**Flex Consumption**, Python 3.11) that POSTs to admin endpoints on the API.

- **Why separate**: in-process APScheduler on `-w 1/2` stole threadpool slots from user requests. Moving it out eliminates contention and lets the API run at `-w 2` comfortably.
- **Flex `alwaysReady` is required for timer reliability (2026-05-06).** Without it the host scales to zero and timer triggers silently miss ticks (App Insights also goes silent because nothing's running to emit telemetry — same root cause for both symptoms). One always-ready instance keyed off `function:drain_outbox=1` keeps the Python worker continuously running; all 18 timers in the app share it. Set via `az functionapp scale config always-ready set --name build-one-scheduler --resource-group buildone_group --settings function:drain_outbox=1`. Costs ~$5–15/mo. **Do NOT use `function_app=1`** — Flex API rejects it; valid groups are only `$http`, `blob`, `durable`, or per-function `function:<name>`.
- **Flex Consumption gotcha (2026-05-06).** Setting `AzureWebJobs.<funcName>.Disabled=true` on a Flex Consumption Function App de-registers that function from host discovery, and setting it back to `false` (or deleting the app-setting) does NOT cause re-registration even after stop+start. Other timers keep firing; the disabled-then-re-enabled one stays missing from `az functionapp function list`. **Don't use that flag on Flex.** Recovery is `func azure functionapp publish build-one-scheduler --python` to force re-discovery. See `docs/runbooks/deploy-restart-timing.md` for the full recovery procedure.
- **Admin endpoints** (see `shared/api/admin.py`): all require `X-Drain-Secret` header.
  - `POST /api/v1/admin/outbox/drain/qbo` — drains QBO outbox (60s); `POST /api/v1/admin/outbox/drain/ms` — drains MS outbox (60s; up to 20 rows / 20s per call); `POST /api/v1/admin/box/drain` — drains Box outbox (60s; up to 20 rows / 20s per call). Per-integration since 2026-06-15. `POST /api/v1/admin/outbox/drain` is the DEPRECATED combined alias (manual fallback, no timer).
  - `POST /api/v1/admin/sync/qbo/{entity}` — one of bill/invoice/purchase/vendorcredit/vendor/customer/item/account/term/company_info. Transactional pulls run every 15 min (purchase at :07/:22/:37/:52), reference pulls 4-hourly. A tick that finds the previous one still running returns `{"status":"skipped","reason":"lock_busy","consecutive_skips":N}` and logs `qbo.sync.skipped_lock_busy` at **WARNING** — every skip is a full cadence of added lag. **Purchase tick cost (2026-10-03):** the per-run QBO Attachable snapshot is bounded by the pull's own watermark (`QboAttachableService(attachables_since=last_sync_time)`; a full/historical pull still takes the full-realm list). ⚠️ The bound is only safe with two companions, both pinned by `tests/test_expense_pull_latency.py`: the late-attach pass (receipts on UNCHANGED purchases — QBO does not bump the parent's LastUpdatedTime on attach) runs on **every** incremental tick including empty ones, because the watermark commits on empty ticks and the next tick cannot see behind it; and a purchase that is NEW locally (deferred, skipped, pulled late) looks back to its own transaction date (`window_since` = `txn_date − CREATE_WINDOW_MARGIN_DAYS`; a receipt cannot predate its purchase), taking the **authoritative** full list only past `CREATE_WINDOW_CAP_DAYS` or with no date. The MS fan-out is enqueued (`expense_pull_fanout`, handler raises a retryable `MsServerError` so real errors back off rather than dead-letter on attempt 1) instead of run inline — so the 5-minute timer is now feasible on the scheduler side. A purchase whose vendor has no `dbo.Vendor` yet is resolved on demand (one `vendor/{id}` GET + the vendor connector): a 200 projects the vendor; a **404 means the payee is a Customer/Employee** (QBO allows it) → plain `ValueError` → permanent skip as before; any other failure raises `VendorNotResolvedError` (non-ValueError → the watermark HOLDS). Before this the miss was always a `ValueError` → permanent skip, and a Ramp-created vendor's first purchase was lost until edited in QBO. Runbook: `docs/runbooks/expense-pull-fanout.md`.
  - `POST /api/v1/admin/reconcile/qbo` — daily
  - `POST /api/v1/admin/reconcile/qbo/billable-status[?dry_run=true]` — hourly :28 (`qbo_billable_status_refresh`, U-718). Re-fetches by id every QBO Bill/Purchase/VendorCredit whose staged lines still say `Billable` and compare-and-sets staging `BillableStatus` (QBO never surfaces an invoice's billable flip through the LastUpdatedTime query or CDC); heals dbo `IsBilled` 0→1 first (Bill, Purchase and, since U-778b, VendorCredit). **Reverse pass (U-778b):** a staged `HasBeenBilled` line whose staged ReimburseCharge says `HasBeenInvoiced=0` (QBO un-invoiced it without touching the source's LastUpdatedTime) is re-fetched live; only on a live `Billable` read carrying the SAME charge id does dbo go `IsBilled` 1→0 (never if any `dbo.InvoiceLineItem` still uses the line — that records a `charge_uninvoiced_locally_billed` issue instead) and then staging CAS `HasBeenBilled`→`Billable`; a flagged line stays a candidate (no CAS) until the local invoice line is gone, then self-heals (unless its source is edited in QBO and re-pulled first — see the runbook); max 50 un-bills per entity per run; counts under `result[<entity>]["reverse"]`. ~15 QBO calls, plus one batched call per 100 reverse-candidate headers per entity.
  - `POST /api/v1/admin/reconcile/qbo/staging-deletes?mode=cdc|full[&dry_run=true]` — CDC hourly :43, full id-diff weekly Sun 06:00 UTC (U-718). Deletes `qbo.*` staging rows ONLY after a GET confirms the record is gone; dbo never written (an Invoice still in dbo gets a `qbo_deleted` issue). Runbook: `docs/runbooks/qbo-staging-freshness.md`.
  - `POST /api/v1/admin/reconcile/ms` — daily
  - `POST /api/v1/admin/expense-coding/sweep-stranded[?apply=true&older_than_seconds=300&limit=100]` — every 15 min at :20 s (`sweep_stranded_coding_suggestions`, U-551b-f1-f5). Drain-secret. Dry-run by default. Re-enqueues `confirmed` coding suggestions whose outbox enqueue was lost (under the suggestion lock, gated by the recode write gate); a dead letter blocks; `error` rows are only reported under `result.recovery`, never re-driven.
  - `POST /api/v1/admin/expense-coding/suggestions/{public_id}/redrive-repoint` — **system-admin JWT** (`require_system_admin()`), not the drain secret, no timer (U-551b-f1-f5). Re-records the SAME approved revision of an `error` repoint as a new ConfirmationSeq and enqueues. 200 `{"data":{status:"enqueued",confirmation_seq}}`; 404 `not_found`; 409 `detail`= `not_error|not_a_repoint|no_repoint_targets|dead_letter_pending|moved|busy|writes_disabled`.
  - `POST /api/v1/admin/expense-coding/suggestions/{public_id}/adopt-written-record` — **system-admin JWT** (`require_system_admin()`), no timer (U-551b-f1-f3b). ADOPTs the written record of a record-less `written` first write (crashed between the QBO POST and the mark): one read-only GET, all-or-nothing line verification (ItemRef + CustomerRef), persists the GET's token + lines via `AdoptCodingSuggestionWrittenRecord` (guarded, seq-fenced). Never writes to QBO. 200 `{"data":{status:"adopted",lines,written_sync_token}}`; 404 `not_found`; 409 `detail`= `writes_disabled|busy|not_written|has_record|not_a_first_write|no_confirmed_coding|legacy|no_live_token|line_holding|line_unmapped|line_not_recoded|line_missing|ambiguous_lines|moved`.
  - `POST /api/v1/admin/time-entry/daily-digest` — emails each worker a summary of a day's time entries + logs for correctness confirmation (default target: **two days ago** in `BUSINESS_TIMEZONE`, set by `TIME_ENTRY_DIGEST_LOOKBACK_DAYS` (default `2`, floored to the default if `< 1`) — gives late ClockOut/Note edits an extra day to settle; `?work_date=YYYY-MM-DD` to re-run a specific day, bypassing the lookback). Once-daily (`time_entry_daily_digest` timer, 13:00 UTC ≈ 8am Central). Enqueues one MS-outbox `send_mail` per worker; idempotent per (worker, day) via a deterministic uuid5 `EntityPublicId`. Honors `TIME_ENTRY_DIGEST_MODE` (off|draft|send — ships off) + `ALLOW_MS_WRITES`.
  - `POST /api/v1/admin/locks/watchdog` — every 5 min at :30 s (`applock_watchdog`, U-784a). Drain-secret. **Report only** (no KILL until U-784b): flags `sp_getapplock` locks that look orphaned by a replaced container (WARNING `applock.orphan_detected` + a deduped `applock_orphan_suspected` `ReconciliationIssue`). Rules + run-level preconditions: `shared/applock_watchdog.py` docstring; SQL permissions: `shared/sql/dbo.applock_watchdog.sql` header (prod = server admin today; never grant `##MS_ServerStateReader##` / VIEW SERVER STATE to the app login or `EXECUTE AS OWNER` these procs). The result carries `watchdog_on_container` (run-level precondition; false = no candidates) and `visibility`. Env: `APPLOCK_WATCHDOG_MODE` (`off`|`report`, default `report`; anything else = report), `APPLOCK_HOST_SILENCE_MIN` (10, floor 5), `APPLOCK_MIN_HOLD_MIN` (10, floor 5). The result carries `visibility` (`limited` = only its own session visible).
  - `GET /api/v1/admin/locks` — **system-admin JWT** (`require_system_admin()`), no timer (U-784a). `{"data":{locks,visibility,watchdog_on_container,settings}}`; read-only.
- **Secret**: `DRAIN_SECRET` env var on both App Service + Function App. Never commit. Rotate if leaked.
- **Rollback to in-process scheduler**: set `ENABLE_SCHEDULER=true` on App Service + restart. Safe — `sp_getapplock` prevents Function + in-process from double-draining.
- **Fail-closed auth**: admin endpoints return 503 when `DRAIN_SECRET` is unset on the server, 401 on mismatch.

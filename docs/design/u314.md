# U-314 design proposal — Phase-6 guarded DROP of the Customer/Project/Vendor QBO identity mapping tables

**Status:** design proposal, no code/SQL changed, no prod mutation. Read-only investigation against current
code (2026-08-25, HEAD `69d4e7b5`, api master) + live production database. **Decision in force:**
`project_qbo_trust_dbo_identity_alone` (umbrella memory, 2026-08-23) — trust `dbo.<Entity>.QboId`/`RealmId`
as the sole identity store; drop the redundant `qbo.*` mapping second-stores. **Precedent:** `docs/design/
wave5.md` (2026-08-24) proposed U-309 → U-310/311/312/313 → this drop unit; all four repoint units shipped
today, 2026-08-25 (batch 5, deployed tip `673b0ad3` / container `63afe188`, restart 08:03:14Z) — Customer
(U-310, `e3e3de60`), Project (U-311, `673b0ad3`), Project's 3 non-identity direct-reads (U-312,
`865a51d1`), Vendor (U-313, `f0d958a4`). U-316 (ROWVERSION race-hardening — the board's own words, "the
drops' gate") is **Gate-2-PASSED but staged for batch 6, not yet deployed** (`69d4e7b5`, on top of the
deployed tip). **Two-phase dispatch, Phase 1** (`feedback_two_phase_dispatch_design_gated`): this document
is the deliverable. No code written, no SQL applied, no branch created.

**Headline finding — corrects the assignment's premise.** The assignment states U-310/U-311/U-313 "stopped
writing" the three mapping tables. **True for Customer and Vendor — false for Project.** `CustomerProject
Connector.heal_missing_mapping()` (kept deliberately by U-311, not an oversight — its own constructor
comment says so) is a **live, reachable write path** into `qbo.CustomerProject`, called from
`InvoiceInvoiceConnector._get_project_public_id` on a genuine dbo-miss during invoice pull (§3.1). A second,
independent finding: `scripts/backfill_qbo_bills.py`'s raw SQL still **reads** `qbo.VendorVendor` directly —
not through any Python wrapper — and will fail to compile the moment the table is gone (§3.2). Both are
real, both are small, and both must ship and soak **before** the DROP, not be silently swept into it.

## 1. Exact drop set + FK dependency order (live, `sys.foreign_keys`, re-run 2026-08-25)

```sql
SELECT fk.name AS fk_name,
       SCHEMA_NAME(tp.schema_id) + '.' + tp.name AS parent_table, cp.name AS parent_col,
       SCHEMA_NAME(tr.schema_id) + '.' + tr.name AS ref_table, cr.name AS ref_col
FROM sys.foreign_keys fk
JOIN sys.foreign_key_columns fkc ON fkc.constraint_object_id = fk.object_id
JOIN sys.tables tp ON tp.object_id = fk.parent_object_id
JOIN sys.columns cp ON cp.object_id = tp.object_id AND cp.column_id = fkc.parent_column_id
JOIN sys.tables tr ON tr.object_id = fk.referenced_object_id
JOIN sys.columns cr ON cr.object_id = tr.object_id AND cr.column_id = fkc.referenced_column_id
WHERE tp.name IN ('CustomerCustomer','CustomerProject','VendorVendor')
   OR tr.name IN ('CustomerCustomer','CustomerProject','VendorVendor');
```

Result — **exactly 6 edges, all outward, none inward** (confirmed live 2026-08-25, matches `wave5.md` §1):

| FK | Parent (child) | Column | References | Column |
|---|---|---|---|---|
| `FK_CustomerCustomer_Customer` | `qbo.CustomerCustomer` | `CustomerId` | `dbo.Customer` | `Id` |
| `FK_CustomerCustomer_QboCustomer` | `qbo.CustomerCustomer` | `QboCustomerId` | `qbo.Customer` | `Id` |
| `FK_CustomerProject_Project` | `qbo.CustomerProject` | `ProjectId` | `dbo.Project` | `Id` |
| `FK_CustomerProject_QboCustomer` | `qbo.CustomerProject` | `QboCustomerId` | `qbo.Customer` | `Id` |
| `FK_VendorVendor_Vendor` | `qbo.VendorVendor` | `VendorId` | `dbo.Vendor` | `Id` |
| `FK_VendorVendor_QboVendor` | `qbo.VendorVendor` | `QboVendorId` | `qbo.Vendor` | `Id` |

Each of the 3 tables is a **leaf junction** — 2 outward FKs of its own (one to its `dbo.<Entity>`, one to
its `qbo.*` staging parent), **zero** tables FK into any of the 3. No cross-table dependency among the
three, either (Customer and Project both point at `qbo.Customer` as *referenced*, never as *parent* of one
another). **Drop order is unconstrained — all 3 can drop in the same batch, any order.**

**Proposed guarded DROP SQL:**

```sql

-- do not trust this document's numbers, they decay the moment it's written.

END;
GO

DROP PROCEDURE IF EXISTS dbo.CreateCustomerCustomer;
DROP PROCEDURE IF EXISTS dbo.ReadCustomerCustomerById;
DROP PROCEDURE IF EXISTS dbo.ReadCustomerCustomerByCustomerId;
DROP PROCEDURE IF EXISTS dbo.ReadCustomerCustomerByQboCustomerId;

DROP PROCEDURE IF EXISTS dbo.DeleteCustomerCustomerById;

DROP PROCEDURE IF EXISTS dbo.CreateCustomerProject;
DROP PROCEDURE IF EXISTS dbo.ReadCustomerProjectById;

DROP PROCEDURE IF EXISTS dbo.ReadCustomerProjectByQboCustomerId;

DROP PROCEDURE IF EXISTS dbo.ReadCustomerProjectIdentityCheckByProjectId;
DROP PROCEDURE IF EXISTS dbo.ReadVendorVendorIdentityCheckByVendorId;
GO
```

## 2. Staging-vs-mapping boundary (the scoping question) — proven per table, not asserted

**In scope (identity JUNCTION tables — dropping):** `qbo.CustomerCustomer`, `qbo.CustomerProject`,
`qbo.VendorVendor`. Each is a 1:1 `(LocalId UNIQUE, QboXId UNIQUE)` pair table with no field data of its
own — see §1's DDL, no columns beyond the two FK ids + audit columns.

**Out of scope (raw STAGING mirrors — do NOT drop):** `qbo.Customer`, `qbo.Vendor`. Live-confirmed still
written on **every pull tick**, independent of any identity-resolution code:

- `scripts/sync_qbo_customer.py::sync_qbo_to_local` calls `qbo_customer_service.sync_from_qbo(realm_id=...,
  sync_to_modules=False)` (line 66) **before** any Customer/Project connector runs. That method routes
  through `QboCustomerRepository.create` / `UpdateQboCustomerByQboId`
  (`integrations/intuit/qbo/customer/persistence/repo.py:120,325`) — an unconditional field-value mirror
  (email, phone, DisplayName, balance, …) of the QBO API response, nothing to do with identity resolution.
- The identical pattern holds for Vendor: `QboVendorRepository.create` / `UpdateQboVendorByQboId`
  (`integrations/intuit/qbo/vendor/persistence/repo.py:136,335`), driven by `scripts/sync_qbo_vendor.py`'s
  own `sync_qbo_to_local`.
- **There is no separate `qbo.Project` staging table at all** — Project is sourced from the same QBO
  Customer API object (`Job=true`), landing in `qbo.Customer` alongside parent customers. One fewer table
  to reason about for Project's boundary.

This matches `wave5.md`'s own scope note (§0) and `docs/staging_removal_phase6_readiness.md`'s Wave 6
classification: retiring the raw mirrors is a materially bigger, unscoped re-architecture (writing straight
into `dbo` without a staging landing table) and stays explicitly out of scope here. Nothing in this drop
touches `qbo.Customer` or `qbo.Vendor` — they keep being staging targets for every future pull tick.

## 3. Zero-WRITER proof — re-derived per family, NOT assumed from the assignment

### 3.1 Project (`qbo.CustomerProject`) — **NOT zero-writer.** The one real blocker.

`CustomerProjectConnector.__init__` (`integrations/intuit/qbo/customer/connector/project/business/
service.py:65`) still holds `self.mapping_repo = mapping_repo or CustomerProjectRepository()`, with its own
comment explaining why: *"heal_missing_mapping/create_mapping/the get_mapping_by_* accessors below still
read+write qbo.CustomerProject (that table isn't dropping in this unit; U-314 is the guarded drop, gated on
soak). Only sync_from_qbo_customer's OWN pull no longer touches it."*

- `create_mapping()` (line 617) is the sole write method: validates the 1:1 constraints via
  `self.mapping_repo.read_by_project_id`/`read_by_qbo_customer_id`, stamps `dbo.Project.QboId` via
  `set_qbo_identity`, then **`self.mapping_repo.create(project_id=..., qbo_customer_id=...)`** — an INSERT
  into `qbo.CustomerProject` (line 659).
- `heal_missing_mapping()` (line 674) is `create_mapping`'s only production caller (line 735) — a U-022
  "heal-don't-delete" discipline: on a **genuine dbo-miss** (no `dbo.Project.QboId` match at all) for a
  job/sub-customer, it name-matches an existing local Project and, if no conflicting identity is found,
  calls `create_mapping` to bind it.
- `heal_missing_mapping()`'s **one production caller** is `InvoiceInvoiceConnector._get_project_public_id`
  (`integrations/intuit/qbo/invoice/connector/invoice/business/service.py:738`), on the invoice-pull path:
  a direct `dbo.Project.QboId` hit is tried first (Option A verify, U-311's own fix) and only falls through
  to the heal-by-name path on a **genuine miss** (no direct hit at all) — never on a failed-verify
  disagreement (Codex-caught P1 during U-311, per that unit's own board note).

  ```
  grep -rn "heal_missing_mapping" --include="*.py" . | grep -v tests
  → integrations/intuit/qbo/invoice/connector/invoice/business/service.py:738  (the only production call)
  → integrations/intuit/qbo/customer/connector/project/business/service.py     (definition + internal call)
  ```

This is deliberate, documented, correctness-motivated code — not an oversight left behind by U-311 — but it
is a live writer today, and it must stop targeting `qbo.CustomerProject` before the DROP is safe. Firing
frequency is low in steady state (`sync_from_qbo_customer`'s own dbo-only fast path stamps a job's
`dbo.Project.QboId` as soon as that customer's own pull tick runs, normally well before any invoice for that
job exists in QBO) — but "rare" is not "zero," and this design must not understate a real write path.

## 4. Zero-READER proof — one live blocker found (Vendor), rest confirmed clean

### 4.1 `scripts/backfill_qbo_bills.py::select_unmapped()` — live, unscheduled, but WILL fail to compile

The raw SQL (lines 111-136) computes its initial `MappedVendorId` via a **hand-rolled join through the
legacy chain**:

```sql
LEFT JOIN qbo.Vendor qv       ON qv.QboId = u.VendorRefValue
LEFT JOIN qbo.VendorVendor vv ON vv.QboVendorId = qv.Id
```

U-313's own comment on this exact code (lines 143-147) is explicit that this was a **deliberate, deferred**
choice, not an oversight: *"try dbo.Vendor's native QboId (dbo-only, re-verified fresh — no legacy
qbo.Vendor -> qbo.VendorVendor fallback left, see resolve_local_vendor_id) for each row's vendor ref; the
MappedVendorId/bucket the raw SQL above computed via its own qbo.Vendor -> qbo.VendorVendor join stays
as-is on a dbo miss."* The dbo-native `resolve_local_vendor_id()` (line 56, already `verify_identity_dbo_
only`-based) only **overrides** the legacy-computed value when it disagrees (lines 160-164) — the initial
CTE still runs the legacy join unconditionally, every invocation. This is a raw, inline SQL string, not a
Python object — `sys.sql_expression_dependencies` (the query in §1) cannot see it, and it will not be caught
by deleting `VendorVendorRepository`; it will simply fail with `Invalid object name 'qbo.VendorVendor'` the
next time an operator runs this script, silently (no test coverage exercises this script's live SQL against
a real DB). **Must be rewritten before the drop** — drop the two `LEFT JOIN`s from the CTE and initialize
`MappedVendorId` as `NULL`, letting `resolve_local_vendor_id()`'s per-row loop (already present, lines
151-175) be the *only* resolution path instead of an override. Mechanical, ~5-line change, no design
question.

`generate_payment_remittance.py` (Vendor's sibling script, same `resolve_local_vendor_id` pattern) has
**zero** references to `qbo.VendorVendor` — fully clean already, confirmed by grep.

# U-300c design proposal — Phase-6 guarded DROP of `qbo.Attachable` / `qbo.AttachableAttachment`

**Status:** design proposal, no code/SQL changed, no prod mutation. Read-only investigation against current
code (2026-08-25, HEAD `69d4e7b5`, api master) + live production database. **Decision in force:**
`project_qbo_trust_dbo_identity_alone` (umbrella memory, 2026-08-23) — trust `dbo.Attachment.QboId`/`RealmId`
as the sole identity store; drop the redundant `qbo.*` mapping/staging second-stores. **Precedent:** U-300a
(dbo-only fast-path primitive) → U-300b (attachable pull repointed off both staging writes) → U-285 (attachable
push repointed off its staging write) → U-315 (dead pull-side mapping-table *read* fallback removed from 3
call sites) → U-316 (ROWVERSION structural hardening — board's own note: "Phase-6 (U-300c/U-307d/U-314) now
unblocked"). This is Attachable's own Phase-6 drop, the pilot family for the whole trust-dbo-alone program.
**Two-phase dispatch, Phase 1** (`feedback_two_phase_dispatch_design_gated`): this document is the deliverable.
No code written, no SQL applied, no branch created.

**Headline finding — corrects and extends the assignment's premise.** The assignment states "0
`qbo.Attachable` + 0 `qbo.AttachableAttachment` creates on pull" (true, U-300b) and treats the two tables as
already redundant second-stores ready to drop. **Writers: fully confirmed zero, on BOTH pull and push** — §2
below re-derives this independently for both directions (the assignment's own premise only asserted the pull
side; the push side needed its own check, since it was still writing as of the 2026-08-21
`staging_removal_phase6_readiness.md` audit and only stopped when U-285 deployed 2026-08-22). **Readers:
NOT yet zero.** One live, unconditional, production code path — `AttachableAttachmentConnector.
sync_attachment_to_qbo`, the push path, called on every Bill/Purchase/VendorCredit attachment upload — still
reads both tables today (§3.1). It is provably behavior-inert for its one live caller (§3.1.2, backed by a
live query), which makes it a small, mechanical, low-risk prerequisite repoint — **but it is not yet shipped**,
and dropping the tables before it ships would break attachment pushes outright (`Invalid object name
'qbo.Attachable'` on literally the next push). §8 Decision 1 proposes this as its own tiny build unit ahead of
the guarded DROP, not folded silently into "the tables are already dead."

## 1. Exact drop set + FK dependency order (live, `sys.foreign_keys`)

Live query, 2026-08-25:

```sql
SELECT fk.name AS fk_name, tp.name AS parent_table, cp.name AS parent_col,
       tr.name AS ref_table, cr.name AS ref_col
FROM sys.foreign_keys fk
JOIN sys.foreign_key_columns fkc ON fkc.constraint_object_id = fk.object_id
JOIN sys.tables tp ON tp.object_id = fk.parent_object_id
JOIN sys.columns cp ON cp.object_id = tp.object_id AND cp.column_id = fkc.parent_column_id
JOIN sys.tables tr ON tr.object_id = fk.referenced_object_id
JOIN sys.columns cr ON cr.object_id = tr.object_id AND cr.column_id = fkc.referenced_column_id
WHERE tp.name IN ('Attachable','AttachableAttachment') OR tr.name IN ('Attachable','AttachableAttachment');
```

Result — **exactly 2 edges, both outward from `AttachableAttachment`, none inward to either table**:

| FK | Parent (child) | Column | References | Column |
|---|---|---|---|---|
| `FK_AttachableAttachment_QboAttachable` | `qbo.AttachableAttachment` | `QboAttachableId` | `qbo.Attachable` | `Id` |
| `FK_AttachableAttachment_Attachment` | `qbo.AttachableAttachment` | `AttachmentId` | `dbo.Attachment` | `Id` |

`AttachableAttachment` is a leaf junction with no children (matches the U-286/`u225_qbo_mapping_fk_gaps.sql`
provenance — this is the exact FK the U-225 migration added). **Drop order: `qbo.AttachableAttachment` first
(clears both outward FKs), then `qbo.Attachable`.** No other family's tables are involved — this is a
same-family, 2-table drop, not a cross-family batch.

**Proposed guarded DROP SQL** (children first, `IF OBJECT_ID` guarded, matching the `IF EXISTS`/`DROP
PROCEDURE IF EXISTS` idiom U-286 already used in these same two files):

```sql
-- Phase-6 drop: qbo.AttachableAttachment (child) before qbo.Attachable (parent).
-- Re-verify §5's live query returns 0 immediately before running this — do not
-- trust this document's row counts, they decay the moment it's written.

IF OBJECT_ID('qbo.AttachableAttachment', 'U') IS NOT NULL
BEGIN
    DROP TABLE [qbo].[AttachableAttachment];
END;
GO

IF OBJECT_ID('qbo.Attachable', 'U') IS NOT NULL
BEGIN
    DROP TABLE [qbo].[Attachable];
END;
GO

-- Sprocs orphaned by the table drop (SQL Server does not require dropping
-- these first — an unbound sproc body only errors at EXECUTE, not at DROP
-- TABLE time — but leaving them live is a footgun: a stray caller gets a
-- confusing runtime error instead of an import-time failure).
DROP PROCEDURE IF EXISTS dbo.CreateQboAttachable;
DROP PROCEDURE IF EXISTS dbo.ReadQboAttachableById;
DROP PROCEDURE IF EXISTS dbo.ReadQboAttachableByQboId;
DROP PROCEDURE IF EXISTS dbo.ReadQboAttachableByQboIdAndRealmId;
DROP PROCEDURE IF EXISTS dbo.UpdateQboAttachableByQboId;
DROP PROCEDURE IF EXISTS dbo.CreateAttachableAttachment;
DROP PROCEDURE IF EXISTS dbo.ReadAttachableAttachmentByAttachmentId;
DROP PROCEDURE IF EXISTS dbo.ReadAttachableAttachmentByQboAttachableId;
DROP PROCEDURE IF EXISTS dbo.DeleteAttachableAttachmentById;
GO
```

(4 sprocs were already retired by U-286 2026-08-20 — `ReadQboAttachablesByEntityRef`,
`ReadQboAttachablesByRealmId`, `DeleteQboAttachableByQboId`, `ReadAttachableAttachmentById` — not repeated
here.)

## 3. Zero-READER proof — NOT fully clean; one live blocker found

### 3.1 `AttachableAttachmentConnector.sync_attachment_to_qbo` (push path) — live, unconditional, blocking

Direct read of lines 605-657: on every call, this method reads **both** tables as "legacy corroboration"
before trusting `dbo.Attachment`'s own identity:

1. `already_dbo_pushed` (dbo already carries `QboId`/`RealmId`) → `QboAttachableRepository().
   read_by_qbo_id_and_realm_id(...)` (line 620-621) — reads `qbo.Attachable`.
2. Regardless of (1)'s outcome, falls through to `self.mapping_repo.read_by_attachment_id(attachment_id)`
   (line 632) — reads `qbo.AttachableAttachment` — then, if found, `qbo_attachable_repo.read_by_id(...)`
   (line 636) — a second `qbo.Attachable` read.

Dropping the tables today would make this method raise `Invalid object name` on the **very next** attachment
push (Bill/Purchase/VendorCredit completion) — a real, immediate production break, not a latent risk.

**3.1.1 — This is genuinely reachable, not dead-by-unreachability.** Its only production caller is
`entities/bill/business/service.py:1984` (`self.attachable_attachment_connector.sync_attachment_to_qbo(...)`),
called on every Bill's attachment-push loop. `grep -rn "sync_attachment_to_qbo("` across the whole tree
(excluding tests) confirms this is the **only** call site — Purchase/VendorCredit route through the same
shared connector method via this one caller's generalized entity_type/entity_id params (confirmed by the
method's own `entity_type`/`entity_id` args, not hardcoded to Bill).

**3.1.2 — But it is provably behavior-inert for that one caller, confirmed against live data, not just code
reachability.** `entities/bill/business/service.py:1984` **discards the return value entirely** — no
assignment, no field read (`synced_attachment_ids.add(attachment_link.attachment_id)` on line 1990 uses the
loop's own local `attachment_link`, not anything from the call). The two legacy reads can only change
*production behavior* if they change which branch fires:
- The mapping-table read (line 632) only matters if reached, i.e. `already_dbo_pushed` is false — which happens
  for a mapped attachment in **either** of two disjoint states (corrected 2026-08-26 after U-300c-prereq's
  adversarial review flagged the realm dimension was originally unchecked): (1) `dbo.Attachment.QboId` is NULL,
  **or** (2) `QboId` is set but `RealmId` is NULL or ≠ the push's target realm (`SetAttachmentQboIdentity`
  preserves a pre-existing NULL RealmId, and `UQ_Attachment_QboId_RealmId` permits `(QboId, NULL)`, so state 2
  is schema-legal). The COMPLETE behavior-inertness invariant covers both:
  ```sql
  SELECT COUNT(*) FROM qbo.AttachableAttachment aa JOIN dbo.Attachment a ON a.Id = aa.AttachmentId
  WHERE a.QboId IS NULL OR a.RealmId IS NULL
     OR a.RealmId <> (SELECT MAX(RealmId) FROM dbo.Attachment WHERE QboId IS NOT NULL AND RealmId IS NOT NULL);
  ```
  **= 0** (re-run live 2026-08-26: all 4193 mapped rows carry the single prod realm `9130353016965726`, none
  NULL, none mismatched). Every legacy mapping row's `dbo.Attachment` already carries its `QboId` **and** its
  `RealmId` (both stamped together on every live QboId-writing path — `_stamp_pushed_identity`, the U-300b pull
  fastpath, and `backfill_qbo_identity_reference.py`, which skips rows whose source staging `RealmId IS NULL`).
  So this branch is unreachable: whenever it would matter, `already_dbo_pushed` is already true and the method
  returns the transient before reaching it — removing the read cannot cause a duplicate QBO upload.
- The `qbo.Attachable` read at line 620-621 fires very often (live count of `dbo.Attachment` rows with a
  QboId/RealmId match in `qbo.Attachable`: **4193 — exactly `dbo.Attachment`'s entire `with_qboid` count**), but
  its only effect is which *object* gets returned (`existing_qbo_attachable` vs. a `_transient_attachable_from_
  dbo(...)`) — both are "don't re-upload" outcomes, and the caller reads neither.

**Net: both legacy reads are live-firing but behaviorally inert for the sole production caller today.** This
makes the fix a mechanical, verifiably behavior-preserving deletion (mirror what the pull side already did in
U-300b: trust `already_dbo_pushed` alone, return the transient object unconditionally) — not a design question.
§8 Decision 1 proposes it as its own tiny prerequisite build unit, not something this drop can silently absorb
(deleting these reads only becomes *provably* safe once it's the actual code doing the dropping's job to prove
it, per this section — the DROP itself must not be the thing that first breaks this path).

### 3.2 `scripts/check_qbo_identity_drift_reference.py` (wrapped by `check_qbo_identity_drift_all.py`) — live, unscheduled, non-blocking-but-noisy

## 6. Soak requirement

**Gating deploy:** §8 Decision 1's prerequisite repoint (removing `sync_attachment_to_qbo`'s two legacy reads)
must ship and deploy first — the DROP cannot safely precede it (§3.1). That unit is small and, per §3.1.2,
provably behavior-preserving against live data before it even ships — it does not need a multi-day soak the way
U-300b's identity-resolution logic did, but it does need to **actually be live** before the DROP runs, plus a
short window to catch anything §3.1.2's live-data proof missed (a `attachment_mapping_orphaned` /
`attachment_upload_failed` `ReconciliationIssue` spike would be the tell — §5 query 3 already checks this).

**Recommended soak, once Decision 1 is deployed:** at least 24h, spanning multiple QBO pull/push cycles across
all three parent families (Bill/Purchase/VendorCredit — attachments have no independent pull cadence of their
own; they ride each parent's own sync timer, per U-316's own finding that "there is no `SyncOutcome`/watermark
for attachables specifically"). Soak-clear bar: §5's query 1 stays at 0 for the full window (no writer
resurfaced), and query 3 stays at 0 (no new reconciliation issue references either table). This mirrors
wave5.md's own 24h/multi-cycle precedent for the sibling customer/project/vendor drop, adjusted for
Attachable's per-parent (not standalone-timer) pull shape.

**Today's standing evidence (§2.4):** zero writes to either table for the ~24h between the U-300b cutover
(2026-08-24 19:26:24Z) and this document (2026-08-25) — a first data point in Attachable's favor, but it
predates Decision 1's own deploy and cannot substitute for the dedicated post-Decision-1 soak window above.

## 7. Rollback note

**No real data loss risk — these are provably redundant second-stores, not a primary record.** If a second
store were ever needed again (not currently anticipated — this is the "one genuinely irreversible call in the
migration," per `project_qbo_trust_dbo_identity_alone`, made deliberately by Chris), it is mechanically
recreatable **empty** from `dbo.Attachment.QboId`/`RealmId` alone:
- `qbo.Attachable` would need to be re-populated by re-pulling each attachable from the live QBO API (the
  `QboAttachableClient`/`query_all_attachables()` machinery is untouched by this drop — only the *local cache*
  of it goes away) — a full-realm re-pull (~19k attachables, ~6 min per the `entities/invoice/intelligence/
  prompt.md` runbook's own BR-MAIN-26 note), not a local restore, since the local rows carried no information
  `dbo.Attachment` + the live QBO API don't already have.
- `qbo.AttachableAttachment` would rebuild trivially as `(AttachmentId, QboAttachableId)` pairs derived
  directly from `dbo.Attachment.QboId` joined back to whatever `qbo.Attachable` re-pull produced above — no
  independent data of its own beyond that join.
- The **schema** itself (table DDL, indexes, sprocs) is fully recoverable from git history even after the base
  SQL files are deleted (§4) — `git show <pre-drop-sha>:integrations/intuit/qbo/attachable/sql/qbo.attachable.sql`
  reconstructs it verbatim, it just needs to be deliberately re-run rather than resurrectable by accident
  (exactly the risk §4 flags for *not* leaving the files in place).

No BLOB, no financial figure, no user-facing record lives in either table — `dbo.Attachment` (the blob
reference + all metadata) and QBO itself (the attachable content) are the two real sources of truth throughout.

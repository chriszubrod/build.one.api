# U-316 design proposal — `run_identity_fastpath_dbo_only` ROWVERSION-race hardening

**Status:** design proposal, no code changed. Read-only investigation against current code (2026-08-25,
HEAD `673b0ad3`) + live prod sproc definitions. **Decision in force:**
`project_qbo_trust_dbo_identity_alone` (umbrella memory). **Precedent cited in the assignment:** U-291
(the mapping-table `run_identity_fastpath`'s watermark-skip fix). **Booked from:** U-310's review,
confirmed-for-investigation by `/em` (BOARD.md, "U-316 (NEW, booked from U-310's review...)").

**Headline finding — corrects the assignment's premise.** The assignment states the gap is "LIVE in
deployed U-307c + U-300b" and that the watermark silently advances past an un-applied update today. It
does not. All **six** dbo-only callers (not two — Customer/U-310, Vendor/U-313, and Project/U-311 are
*also* live as of this exact deployed tip, `673b0ad3`/`63afe188`, per BOARD.md's own "entire QBO
identity-repoint migration... now deployed dbo-only" milestone note) already contain a hand-written guard,
present since each connector's very first commit, that catches both the apply-path and the stamp-path
`entity is None` outcome and raises `RuntimeError` before returning to the caller — which correctly holds
the watermark. §1 proves this file-by-file, with git provenance. There is **no live bug and no exposure to
remediate** (§4). The real, still-open risk is structural, not behavioral: nothing in the shared primitive
*enforces* that guard, so it is currently hand-copied six times — precisely the anti-pattern the module's
own docstring warns "is how a fix goes unnoticed... it already did, twice." §2 proposes closing that
structurally, mirroring U-291's precedent as directed. This is a hardening/hygiene unit, not a hotfix.

---

## 1. Precise characterization

### 1.1 The APPLY path — does it ever actually return `None`?

`_apply()` inside `run_identity_fastpath_dbo_only` (`identity_fastpath.py:625-638`) calls the caller's
`apply_fields(row)`. If that returns `None`, it fires `on_apply_returned_none` (if wired) and returns
`FastPathOutcome(hit=True, entity=None)`. Whether this branch is *reachable* depends entirely on how the
caller's `apply_fields` is implemented — and, read against the actual `Update<Entity>ById` sprocs, it is
**not uniform across the six families**:

| Family | `apply_fields` → underlying UPDATE sproc | Conflict signal | Can `apply_fields` return `None`? |
|---|---|---|---|
| Vendor (U-313) | `_apply_vendor_fields_and_sync` → `UpdateVendorById` | `IF NOT EXISTS (...RowVersion...) BEGIN ROLLBACK; RAISERROR(...); RETURN; END` | **No** — raises before returning (see 1.1.1) |
| Project (U-311) | `_apply_project_fields_and_sync` → `UpdateProjectById` | `OUTPUT` on `UPDATE ... WHERE Id=@Id AND RowVersion=@RowVersion`, no `RAISERROR` | Sproc-level yes, but the method itself checks and raises internally (see 1.1.2) — never returns `None` to the primitive |
| Customer (U-310) | `_apply_customer_fields_and_sync` → `UpdateCustomerById` | Same OUTPUT/no-guard shape as Project | **Yes** — reachable |
| CostCode (U-307c) | `_apply_cost_code_fields_and_sync` → `UpdateCostCodeById` | `WHERE Id=@Id AND RowVersion=@RowVersion; IF @@ROWCOUNT>0 SELECT ...` (SELECT skipped on conflict → no result set) | **Yes** — reachable |
| SubCostCode (U-307c) | `_apply_sub_cost_code_fields_and_sync` → `UpdateSubCostCodeById` | Identical shape to CostCode | **Yes** — reachable |
| Attachment (U-300b) | `_verify_or_heal_pulled_blob` → `AttachmentRepository.update_by_id` → `UpdateAttachmentById` | Same OUTPUT/no-guard shape as Customer/Project | **Yes** — reachable |

So the assignment's premise that "`apply_fields` returning `None`" is *the* race scenario is only literally
true for 4 of 6 families. For Vendor it is unreachable (the sproc raises). For Project the connector's own
`apply_fields` wrapper already intercepts the `None` and raises before the primitive ever sees it (1.1.2).

**1.1.1 — Vendor is the one family where a ROWVERSION conflict is DB-raised, not silently absorbed.**
`UpdateVendorById` (`entities/vendor/sql/dbo.vendor.sql:300-330`) explicitly checks
`RowVersion = @RowVersion` and, on mismatch, `ROLLBACK TRANSACTION; RAISERROR('Concurrency conflict...',
16, 1); RETURN;`. `VendorRepository.update_by_id` (`entities/vendor/persistence/repo.py:238-271`) wraps the
call in `try/except Exception as error: raise map_database_error(error)` — it does not catch-and-return-None.
`map_database_error` (`shared/database.py:140-172`) classifies the RAISERROR text via `CONCURRENCY_KEYWORDS`
(`'concurrency', 'conflict', ...`) into `DatabaseConcurrencyError`, a plain `DatabaseError` subclass with no
`is_retryable` attribute. That exception propagates *uncaught* through `_apply()`, through
`run_identity_fastpath_dbo_only`, through `VendorVendorConnector.sync_from_qbo_vendor` (nothing in that call
chain catches it), to `project_records`'s per-record `try/except` (`base/sync_outcome.py:45-57`), which calls
`outcome.record_projection_error(qbo_id, e, ...)`. `record_projection_error`'s three-rule classifier
(`base/sync_outcome.py:117-168`) checks `is_retryable_error` first (false — `DatabaseConcurrencyError` has no
`is_retryable` flag and doesn't match `is_transient_error`'s connection/timeout substrings), then
`isinstance(error, ValueError)` (false), landing on rule 3 (**hold**). **Net effect: a Vendor ROWVERSION race
today already holds the watermark, via the database layer, without ever touching the `on_apply_returned_none`
/ `entity is None` machinery at all.**

*Side note, out of scope for this unit:* `UpdateVendorById`'s `ROLLBACK TRANSACTION` inside the sproc appears
to contradict the standing convention documented in `build.one.api/CLAUDE.md` ("NEVER `ROLLBACK TRANSACTION`
inside a sproc — pyodbc runs autocommit-off... SQL Server raises error 266"). Whether this actually manifests
error 266 in practice (vs. the intended `RAISERROR` text reaching the client cleanly) was not verified against
live SQL Server behavior — it's a different surface (sproc transaction hygiene, not the identity fast path)
and is flagged in §5 as a candidate follow-up, not fixed here.

**1.1.2 — Project's `apply_fields` wrapper already closed this itself, independently, citing U-291.**
`_apply_project_fields_and_sync` (`customer/connector/project/business/service.py:460-489`) calls
`update_by_id`, then:
```python
updated = self.project_service.repo.update_by_id(project)
if updated is None:
    raise_concurrent_write_race(entity_label="Project", entity_id=project.id, path_label=path_label)
```
Its own docstring: *"every one of them gets the same ROWVERSION-race guard for free (U-291) — a caller cannot
forget to check for a `None` `update_by_id` return, because there is nothing to check: this method raises
instead of returning it."* This is the U-291 pattern already applied at the `apply_fields`-implementation
level for Project — which means the connector's separately-wired `on_apply_returned_none=lambda entity:
raise_concurrent_write_race(...)` (line ~138) is dead code (unreachable — `apply_fields` never returns `None`
for this family).

**1.1.3 — Customer, CostCode, SubCostCode, Attachment: `apply_fields` CAN return `None`, and this is where
the assignment's premise is literally correct for the apply path.** Their sprocs signal a conflict by
returning zero output rows, not by raising. `Customer` and `Attachment` wire `on_apply_returned_none`... no —
correction, only **Customer** wires it (`customer/connector/customer/business/service.py:84`); **CostCode,
SubCostCode, and Attachment wire none.** For these three, `_apply()` returns
`FastPathOutcome(hit=True, entity=None)` with no callback fired. This is where the "wire ZERO race hook"
half of the assignment's claim is accurate.

### 1.2 The STAMP path — does `Set<Entity>QboIdentity` detect a race?

**No. None of the six `Set<Entity>QboIdentity` sprocs are ROWVERSION-guarded.** All six
(`entities/{vendor,customer,cost_code,sub_cost_code,project,attachment}/sql/dbo.*.sql`) share the identical
shape:
```sql
UPDATE dbo.[Entity] SET [QboId]=NULL, [RealmId]=NULL, ...
  WHERE [Id] <> @Id AND [QboId] = @QboId AND ([RealmId] = @RealmId OR (...NULL...));  -- theft-clear
IF @@ROWCOUNT > 0 SET @Stolen = 1;

UPDATE dbo.[Entity] SET [QboId] = CASE WHEN @QboId IS NOT NULL THEN @QboId ELSE [QboId] END, ...
  OUTPUT INSERTED.[Id], ...
  WHERE [Id] = @Id AND ( (@QboId IS NOT NULL AND ([QboId] IS NULL OR [QboId]<>@QboId)) OR (...RealmId...) );
```
This is a **blind `UPDATE ... WHERE [Id] = @Id`** — it never checks `RowVersion`, so a concurrent edit to any
*other* column on the target row cannot block or be detected by this statement; it only touches
QboId/RealmId(/Active). The `IF ... IS NULL OR <> @Value` guard is an **idempotency** check (skip the write if
the row already carries this exact identity — harmless, not a race signal), not a concurrency check. So the
premise "is `Set<Entity>QboIdentity` ROWVERSION-guarded" — **no, categorically**, for all six families
uniformly.

**The actual STAMP-path race is narrower than a field-edit ROWVERSION conflict: it's the candidate row being
deleted between `resolve_candidate()` returning it and the stamp lock acquiring.** Every `_stamp_*_identity`
method (`_stamp_vendor_identity`, `_stamp_customer_identity`, `_stamp_cost_code_identity`,
`_stamp_sub_cost_code_identity`, `_stamp_project_identity`, `_stamp_pulled_identity`) runs under its own
per-candidate-id `qbo_app_lock`, re-reads the candidate via `read_by_id` inside that lock, and (for Vendor,
Customer, Project — explicitly; for the other three, implicitly via the tail `read_by_id` after a no-op
`set_qbo_identity` call against a nonexistent Id) returns `None` if the row is gone. Since
`Set<Entity>QboIdentity` itself never signals success/failure (its Python wrapper discards the sproc's
`OUTPUT`; the Attachment version's own docstring says this outright: *"Wraps `AttachmentRepository.
set_qbo_identity` (returns `None`)"*), the **only** way `stamp_identity` produces `None` is this
presence-check, for **all six families identically** — and `run_identity_fastpath_dbo_only` itself never
inspects `stamped` before wrapping it: `stamped = stamp_identity(candidate); return FastPathOutcome(hit=True,
entity=stamped)` (`identity_fastpath.py:663-665`). This confirms the assignment's premise #2 exactly as
stated: the primitive does not check the stamp path at all, for any of the six.

### 1.3 What actually prevents a silent skip today

Despite §1.1/§1.2, no watermark silently advances past a race today, because **every one of the six
callers** — not just some — carries this identical block immediately after the `run_identity_fastpath_dbo_only`
call, differing only in the entity name and f-string:
```python
if outcome.entity is None:
    # Only reachable via a concurrent-delete/ROWVERSION race inside ..., or a
    # falsy qbo_id -- ...
    raise RuntimeError(f"Failed to resolve {Entity} for {External} ... via the dbo-only identity fast path")
```
File:line for each: `vendor/connector/vendor/business/service.py:106`,
`customer/connector/customer/business/service.py:94`, `customer/connector/project/business/service.py:154`,
`item/connector/cost_code/business/service.py:91`, `item/connector/sub_cost_code/business/service.py:145`,
`attachable/connector/attachment/business/service.py:92`. This external check catches **both** paths — the
apply-path `entity=None` (for the 3 families where it's reachable) and the stamp-path `entity=None` (for all
6) — because both flow through the same `outcome.entity` field regardless of which branch produced the
`None`. `RuntimeError` is correctly classified by `record_projection_error` rule 3 → hold, for the five
families whose pull loops route through `project_records`/`SyncOutcome` (Vendor, Customer, Project, CostCode,
SubCostCode — confirmed via `project_one=connector.sync_from_qbo_*` at
`item/business/service.py:180,200`, `customer/business/service.py:237,257`, `vendor/business/service.py:211`,
and Project's equivalent).

**`git log -p` confirms this check was part of each connector's very first commit that introduced
`run_identity_fastpath_dbo_only` usage** — e.g. CostCode's block was added in `fc3d0a39`, the exact commit
BOARD.md records as "U-307c-build... Shipped" — not a later patch. There was never a window where these
connectors were live without this guard.

**Attachment is a structurally different case worth calling out precisely** (still safe, but for a different
reason): `AttachableAttachmentConnector.sync_from_qbo_attachable` raises `RuntimeError` the same way, but its
caller, `QboAttachableService._sync_to_attachments` (`attachable/business/service.py:299-319`), wraps each
attachable in its own `try/except Exception: logger.error(...)` and simply omits it from the `healthy` list —
**there is no `SyncOutcome`/watermark for attachables specifically**; attachments are pulled per-parent
(Bill/Purchase/VendorCredit) inline with that parent's own pull, or via the full-realm `sync_from_qbo`, both
already documented as "best-effort: the parent entity still projects." So a stamp/apply race on an attachment
today means "this one attachable is skipped for this pull attempt, logged, and naturally retried the next
time its parent (or the full realm) is pulled" — not "a watermark advances past it forever." No watermark
corruption is possible here because there is no per-attachable watermark to advance.

## 2. The fix — mirroring U-291's precedent, made structural

U-291's fix to `run_identity_fastpath` (the mapping-table sibling) did two things: (a) hoisted the
`None`-check to fire on **any** `apply_fields`-returns-`None` outcome, unconditionally, regardless of mapping
state, and (b) extracted `raise_concurrent_write_race` as the one shared raise every family reuses. The
equivalent close for `run_identity_fastpath_dbo_only` is:

1. **Make the apply-path raise unconditional, not opt-in.** In `_apply()`, when `updated is None`: call
   `on_apply_returned_none(row)` if provided (kept for a future family that needs a pre-raise side effect —
   see Decision 2 below on whether to keep the param at all), then **always** call
   `raise_concurrent_write_race(entity_label=entity_label, entity_id=row.id, path_label="dbo-only fast path")`
   — not conditioned on whether a callback was passed. A caller can no longer omit protection by omitting the
   parameter, and a caller whose callback logs-but-forgets-to-raise no longer accidentally reintroduces the
   silent skip.
2. **Add the missing stamp-path check**, symmetric to (1): after `stamped = stamp_identity(candidate)`,
   `if stamped is None: raise_concurrent_write_race(entity_label=entity_label, entity_id=candidate.id,
   path_label="dbo-only fast path (stamp)")` before constructing the returned `FastPathOutcome`.
3. **Reuse `raise_concurrent_write_race`** (already imported by `identity_fastpath.py`, already the shared
   raise for the mapping-table sibling and for Project's/Customer's/Vendor's existing wiring) — no new
   exception type, no hand-rolled raise.

After this change, `run_identity_fastpath_dbo_only` can **never** return `FastPathOutcome(hit=True,
entity=None)` — the only way to observe `entity is None` is `hit=False` (a falsy `qbo_id`, an already-excluded
case per every connector's own upstream guard). This is a strictly stronger guarantee than today's patchwork
of "DB-level raise for some families, unwired-primitive-fallback-but-caught-by-hand-copied-caller-check for
others" — and it collapses three different code paths producing the same observable outcome into one.

## 3. Blast radius across all 6 dbo-only callers

**All six benefit from the primitive-level fix immediately, with zero per-caller code required for
correctness** — that is the entire point of it being a shared primitive; every caller already imports and
calls the same function. Enumerated call sites (confirmed live at HEAD `673b0ad3`):

| # | Family | Unit | File:line | `on_apply_returned_none` wired today? | External `outcome.entity is None` check present today? |
|---|---|---|---|---|---|
| 1 | Attachment | U-300b | `attachable/connector/attachment/business/service.py:77` | No | Yes |
| 2 | CostCode | U-307c | `item/connector/cost_code/business/service.py:71` | No | Yes |
| 3 | SubCostCode | U-307c | `item/connector/sub_cost_code/business/service.py:117` | No | Yes |
| 4 | Customer | U-310 | `customer/connector/customer/business/service.py:74` | Yes | Yes |
| 5 | Project | U-311 | `customer/connector/project/business/service.py:123` | Yes (dead — see 1.1.2) | Yes |
| 6 | Vendor | U-313 | `vendor/connector/vendor/business/service.py:86` | Yes (dead — see 1.1.1) | Yes |

**Behavior-preserving confirmation:** for every one of the 6, today's *observed* outcome on a genuine race is
already "raise RuntimeError (or DatabaseConcurrencyError for Vendor) → watermark holds" — proven per-family in
§1, not assumed. The structural fix produces the exact same observable outcome through one canonical path
instead of three overlapping ones (DB-raise / wired-callback / unwired-fallback-caught-by-caller). No
caller's *behavior* changes; what changes is *where the guarantee lives*.

**Recommended (not required) per-caller cleanup, bundled into the same unit — see Decision 4:** once the
primitive guarantees `entity is None` is unreachable for `hit=True`, each of the 6 callers' own
`if outcome.entity is None: raise RuntimeError(...)` blocks becomes literally unreachable dead code, as do
Customer's/Project's/Vendor's `on_apply_returned_none=lambda entity: raise_concurrent_write_race(...)`
wirings and Project's own internal `if updated is None: raise_concurrent_write_race(...)` (§1.1.2 — this one
specifically becomes fully redundant once the primitive raises for it too). Leaving hand-copied-but-now-dead
guards in place is its own small hazard: a future reader could reasonably (and wrongly) conclude the
primitive still needs caller-side protection, or copy the pattern into a 7th caller under the same
misapprehension this doc corrects.

## 4. Deployed-exposure remediation

**None needed.** §1.3 establishes that all six callers have carried a functioning guard since their
respective first commits (`fc3d0a39` for U-307c, and the equivalent origin commits for U-300b/U-310/U-311/
U-313 — same pattern, same provenance). No watermark has silently advanced past an un-applied update for any
of these six families at any point since each shipped. There is nothing to re-pull, no `ReconciliationIssue`
backfill, no watermark rewind. This directly contradicts the assignment's framing ("LIVE in deployed U-307c +
U-300b") — the factual half of that framing (no `on_apply_returned_none` wired for those two, true) does not
imply the behavioral half (watermark silently advances, false), because the caller-side check was always
there to catch it independently.

## 5. Decisions needing /em sign-off

**Decision 1 — proceed given the corrected characterization?**
The assignment treated this as urgent (must close before Phase-6 drops, described as a live gap). Given §1-4,
it is not live. **Recommendation: still do it**, but as a structural-safety/hygiene unit, not urgency-driven —
it closes the exact hand-copy-drift failure mode this module's own docstring warns about (twice-already-bitten
per U-276/U-277), and it is cheap (one shared-function change + optional mechanical caller cleanup) relative
to the risk it forecloses for any future 7th dbo-only adopter. Keep it sequenced before Phase-6
(U-300c/U-307d/U-314) per the board's existing note — no reason to relax that, since the fix is strictly
additive safety with no downside to landing early.

**Decision 2 — keep `on_apply_returned_none` as a parameter, or remove it?**
Every current usage of this callback (Customer/Project/Vendor, 3 sites) does nothing but call
`raise_concurrent_write_race` directly — no family-specific logging or side effect. Once the raise is
structural, the parameter adds no behavior today.
**Recommendation: keep it**, as a cheap optional pre-raise hook for a future family that might need one (e.g.
a metric increment before the raise), rather than force an API removal across 3 call sites for zero present
benefit. Low-stakes either way — flagging because it's a real fork, not a default I should silently pick.

**Decision 3 — bundle the 6 callers' dead-code cleanup into this same unit, or defer to `/simplify`?**
**Recommendation: same unit.** The deletions are small (a 6-8 line block × 6, plus 3 one-line
`on_apply_returned_none=` kwargs, plus Project's 2-line internal `if updated is None: raise...`), entirely
mechanical, and behavior-preserving by construction (§3's table already proves each is dead once the
primitive change lands) — well inside what `/em`'s own Pass-2 discretion allows folding into Pass 1 when the
diff is this contained. Deferring only postpones an outcome that isn't in question.

**Decision 4 — the Vendor `ROLLBACK TRANSACTION` finding (§1.1.1 side note)?**
Out of scope for U-316 (different surface: `UpdateVendorById`'s own transaction hygiene, not the identity
fast path), discovered incidentally during this investigation, not verified against live SQL Server behavior.
**Recommendation: book as its own follow-up in TODO.md**, tagged for whoever next touches Vendor's sproc or
investigates a Vendor-update-related anomaly — not fixed here, per two-phase design-gated discipline (this
unit's deliverable is the doc, not incidental code).

## 6. Unit breakdown

**One build unit**, not split per family. Rationale: the correctness-bearing change is entirely in
`identity_fastpath.py` (§2, ~10 lines); the per-caller work (§3 Decision 3) is uniform, mechanical, and
low-risk (deleting now-provably-dead code, not adding logic) across all 6 — splitting into 6 units would add
coordination overhead with no corresponding risk reduction, unlike Wave 5's family units (U-310/U-311/U-312),
which were split because each carried distinct connector-specific design work (name-match adopt logic,
parent-customer resolution, etc.). This unit has none of that; it's one shared-primitive fix propagating
uniformly.

**Tier: P0-surface** (concurrency/ROWVERSION-adjacent, touches every currently-deployed dbo-only QBO pull
path) — build directly, not via Composer, per the `/em` tier rubric. **Reviewer: Codex `xhigh`.**

**Test coverage:** extend `tests/test_u300a_identity_fastpath_dbo_only.py` (the primitive's own suite) with
two new mutation-proven cases — `apply_fields` returning `None` with no `on_apply_returned_none` wired now
raises (currently would silently return `entity=None`, prove red-before-fix by reverting), and
`stamp_identity` returning `None` now raises (currently unchecked, same red-before-fix proof). Per-family
connector tests (`test_u289_item_qbo_identity_repoint.py`, `test_u290_vendor_qbo_identity_repoint.py`,
`test_u276_customer_project_qbo_identity_repoint.py`, `test_u279_attachment_qbo_identity_repoint.py`) that
assert on the now-dead caller-side `RuntimeError` message text should be checked for continued pass (the
`RuntimeError` still fires, just from inside the primitive with a slightly different message — assert on
type/hold-classification, not exact string, going forward) rather than assumed unaffected.

**Sequencing:** before U-300c/U-307d/U-314 (Phase-6 guarded drops), exactly as BOARD.md already notes. Any
future 7th dbo-only adopter (a hypothetical Wave-6 family) automatically inherits the guarantee with zero
extra work once this lands — a pure forward win, no reason to gate it on anything else.

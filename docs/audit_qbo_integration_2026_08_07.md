### auth — QBO OAuth & token lifecycle

This subsystem is a two-layer sandwich: a well-engineered 2026 hardening layer (sp_getapplock single-flight refresh with re-read-under-lock, Fernet encryption at rest with plaintext self-heal and key-mismatch fail-closed, HMAC-signed CSRF state, typed error taxonomy, a real runbook with expiry alerts) wrapped around a legacy OAuth helper module (external/client.py) that still uses in-band dict status-code sentinels, has no timeout on 3 of its 4 HTTP calls, shadows its own imported discovery function, and hard-codes the prod redirect URI. ### sql — QBO SQL layer (qbo.* sprocs, staging/mapping tables, outbox, watermark, migrations)

The qbo.* SQL layer is structurally consistent and shows real, incident-driven hardening: every mapping table enforces one-to-one uniqueness in both keyspaces, updates are ROWVERSION-CAS-guarded, the outbox claim uses a correct UPDLOCK/READPAST/ROWLOCK pattern, and keyspace discipline (qbo.Id vs dbo.Id) is clean in every cross-schema join I checked. However, the hardening is reactive and never propagated to siblings: unique (QboId, RealmId) staging constraints exist only on the three entities that already had duplication incidents (VendorCredit, Invoice, Attachable) while Bill/Purchase/Vendor/Customer/Item/Account/Term/ReimburseCharge remain unprotected read-then-insert upserts; FK enforcement on mapping tables exists only for Purchase and VendorCredit; and the VendorCredit line UPDATE diverges from the guarded Bill/Purchase pattern. There is no TRY/CATCH or SET XACT_ABORT anywhere in the layer, and read sprocs cargo-cult BEGIN TRANSACTION/COMMIT around plain SELECTs. The most acute operational risk is an ad-hoc mass UPDATE of dbo.BillLineItem.IsBillable left embedded at the tail of the re-runnable Bill base file — it silently re-fires on every routine re-apply of that file. Base-file-vs-prod drift is an acknowledged, only partially ratcheted risk (the reconciliation base file carries an explicit "may be stale, do NOT re-apply wholesale" banner).

**Strengths:**
- Mapping tables uniformly enforce UNIQUE on BOTH the dbo-side and qbo-side id columns (e.g. UQ_BillBill_BillId/UQ_BillBill_QboBillId), structurally preventing duplicate mappings and doubling as covering indexes for the hot by-id lookups
- Outbox dequeue (ClaimNextPendingQboOutbox, qbo.outbox.sql:341-398) uses a correct TOP 1 + UPDLOCK/READPAST/ROWLOCK claim inside one transaction, with a well-commented always-return-a-result-set shape for pyodbc, plus a filtered drain index matching the claim predicate
- Keyspace discipline is clean in every SQL join inspected (ReadExpenseCodingQueue, ReadQboPurchaseLinesNeedingUpdate, the IsBillable backfill) — all hop qbo.*Id -> mapping -> dbo.*Id correctly; qbo.reimburse_charge.sql documents the keyspace contract in-file

- Optimistic concurrency (WHERE ... AND RowVersion = @RowVersion) is applied on nearly all header/line UPDATE sprocs, and money columns are consistently DECIMAL(18,2) with rates at (18,6)
- Static test guards exist for the sproc contract: test_repo_sproc_param_contract.py verifies every repo-bound param is declared by some .sql definition (covers qbo schema), and test_sproc_single_source.py + sproc_drift_ledger.py freeze the known duplicated VendorCredit sproc bodies as non-growable debt

## Slice assessments

### pull-txn — QBO transactional pull scripts (bill, purchase, invoice, vendorcredit, reimburse_charge)

The five transactional pulls are a copy-paste family at visibly different hardening generations: bill is the flagship (hold-on-failure watermark, permanent-skip vs transient-fail taxonomy, pull-race ride-out, reconciler backstop, batched Box/SP/Excel fan-out), purchase and vendorcredit are near-clones with deliberate parity comments, invoice is a generation behind (no failure hold, no taxonomy, no ride-out, full-table line preload), and reimburse_charge is a minimal but contract-correct staging capture — the only script whose watermark hold also covers staging-tier failures. The central structural weakness is that the hold-on-failure discipline the scripts advertise only guards the module-projection tier: the service-layer sync_from_qbo calls beneath bill/purchase/vendorcredit swallow staging upsert failures into log-only lists, so the watermark can advance past records that never landed in qbo.* at all — with no reconciler backstop for purchase or vendorcredit. Consistency drift is real and operational (end_date ordering splits 2-vs-2 across scripts, vendorcredit's attachment path is dead code, its connector alone launders transient DB errors into permanent skips), meaning an operator cannot reason about one script from another's behavior. Concurrency protection is thin: no applock serializes same-entity pulls and dbo.Sync has no uniqueness on (Provider,Env,Entity), so the timer+manual-admin overlap case both re-arms the known pull race and can defeat a concurrent run's watermark hold. U-211 breaker behavior is acceptable at the fetch phase (raise → outer except → 500 → watermark untouched) in all five; the known swallow points are the booked per-record attachable loops. Under the staging-deletion program, four scripts port cleanly (API→dbo direct actually deletes the pull-race class the ride-out machinery exists for), but reimburse_charge is a hard exception: its entire purpose is durable qbo.ReimburseCharge capture of one-shot data with no dbo target, so the program needs an explicit exemption or a dbo home for it before Phase 4.

### pull-ref — QBO sync scripts — reference pulls (vendor, customer, item, account, term, company_info)

The six reference pulls are a consistent, conservative one-way pattern — watermark-incremental QBO query, staging upsert, per-record connector projection into dbo — and the authz matrix is clean at both entry points (assert_cli_system_admin under __main__ in all six; the admin route's async _require_drain_secret at shared/api/admin.py:80 sets is_system_admin and _timed's asyncio.to_thread at admin.py:87 carries the ContextVar into the worker). None of them does an unconditional SELECT-*-every-run: all pass the stored watermark, so steady-state cost is roughly 31 QBO queries/day for the whole slice (5 entities at 4h cadence + daily company_info) — negligible against the 500K cap, and even a watermark-reset full pull is one or two 1000-row pages per entity. The real risks are omission-shaped: every client's query is structurally blind to QBO deactivation/merge (no `Active IN (true,false)`, and 4 of 5 entities have no reconcile path at all), and per-record projection failures are swallowed while the watermark advances — for low-churn reference data that means permanent staleness, not next-tick self-heal. The memory-listed company_info empty-response ValidationError is FIXED in the current path (client raises ValueError at company_info/external/client.py:125, service returns None at business/service.py:49-54, script advances the timestamp cleanly). Code maturity is uneven: account is the most hardened (argparse, dry-run, RowVersion-conflict retry), company_info the crustiest (stray print(), inline duplication), and vendor/customer/item/term carry ~150 lines each of copy-pasted helpers plus dead push-path scaffolding. ### push — QBO sync script layer — push-side (local→QBO) paths reachable from scripts

The push-side surface is a graveyard with one live landmine. ### orchestration — Entry points, scheduling, and operational envelope (QBO sync script layer)

The layer has exactly three entry-point families — Azure Function timers (function_app.py) POSTing to /api/v1/admin/sync/qbo/{entity} (DRAIN_SECRET-gated, sets system authz, runs the whole script inline in the request via asyncio.to_thread), CLI __main__ (assert_cli_system_admin everywhere except reconcile_project.py, already filed), and the dormant in-process APScheduler fallback (shared/scheduler.py) — and their guarantees are inconsistent: the HTTP path sets authz and reports envelopes, the fallback path sets no authz at all, and nothing anywhere serializes two pulls of the same entity. The operational envelope is held together by unenforced timing assumptions: the scheduler abandons any run after 60s (REQUEST_TIMEOUT_SECONDS), the App Service gateway kills responses at 240s, yet the actual sync thread runs unbounded and the 15-minute timers will happily start a second concurrent run against the same watermark — the admin endpoint's own "attachments=false" escape hatch is written proof that attachment-heavy runs blow these windows. Observability is two-tier: whole-run failures surface cleanly (script returns status_code 500 → endpoint 502 → scheduler failure log), but per-record failures, silent watermark holds, silently-dead vendorcredit attachment sync, and silently-failed optimistic watermark writes are visible only as INFO/WARNING lines in App Service logs that no alert reads. ### S-01 [P2] [pull-txn] Watermark hold does not cover staging-tier upsert failures (bill/purchase/vendorcredit)
**Location:** `integrations/intuit/qbo/bill/business/service.py:97`

QboBillService.sync_from_qbo catches every per-record staging upsert exception into a log-only failed_bills list (service.py:97-108) and returns only synced_bills; QboPurchaseService (purchase/business/service.py:98-109) and QboVendorCreditService (vendorcredit/business/service.py:75-77, which `continue`s) do the same.

# QBO pull rules + invoice specifics

The two 'rule of three' pull invariants (never clobber a human edit, never delete-then-create on an empty read), the keyspace separation, and the invoice pull/packet/push surface.

---

- **QBO sync mappings**: `sync_to_qbo_bill()` must create `BillLineItemBillLine` mappings after storing QboBillLines, using `line_num` to correlate local BillLineItems with QBO API response lines. Without these mappings, subsequent `sync_from_qbo` creates duplicate BillLineItems
- **QBO pull must not clobber a human-edited document number ("rule of three", U-027)**: the pull connectors derive the document number as `qbo.doc_number or f"QBO-{qbo_id}"`. On the **UPDATE path** never pass that derived value straight through — a scheduler re-pull would revert a local human correction within one tick (KI-42). Route it through the shared pure helper `integrations/intuit/qbo/base/field_ownership.py::preserve_human_edited_ref(stored, incoming, qbo_id)`, which keeps the stored value unless it is empty/null or the exact `QBO-<qbo_id>` placeholder (which still upgrades to a real doc_number). Applied to **Bill.bill_number**, **BillCredit.credit_number**, **Expense.reference_number** (U-024), and **Invoice.invoice_number** (U-034 — with the fingerprint + provenance adopt guard described below). **CREATE paths stay unchanged** (always the QBO-derived value). Any new QBO pull connector with a human-editable number must reuse this helper. **Caveat — do NOT blindly apply it to a connector whose lost-mapping recovery keys on the QBO-derived number.** `Invoice.invoice_number` was the tricky case (its gap-detect/adopt path `read_by_invoice_number_and_project_id` keyed on the QBO-derived number, so a naive preserve reintroduced the "46 phantom -N invoices" bug — U-027 deferred it). **Resolved (U-034):** the adopt path now falls back to a header **fingerprint** (total within `Decimal("0.01")` + txn_date + project) when the number lookup misses, and requires **QBO-line-provenance** (`_has_qbo_line_provenance` — the invoice carries ≥1 `InvoiceLineItemInvoiceLine` line-mapping) on BOTH adopt routes before binding — so a human-renamed, mapping-lost invoice is RE-ADOPTED (not phantom-duplicated) while a distinct **manual** invoice (which stays unmapped because Invoice→QBO push is disabled) is never wrongly adopted. Preserve is applied on both the plain UPDATE and the adopt UPDATE. Connector-only, no schema change. Bill/VendorCredit carry a narrower documented residual (their `(vendor, number)` create-dedup is only defeated if a mapping is abnormally lost while the entity persists). See TODO.md.
- **QBO pull "heal-don't-delete" on a mapping-exists-but-entity-read-empty ("rule of three" COMPLETE — U-022 customer→Project, U-029 purchase→Expense, U-031 Bill + VendorCredit)**: a pull connector must NEVER `mapping_repo.delete_by_id(...)` then fall through to CREATE when the mapping's bound entity reads empty — a *transient* empty-read then mints a DUPLICATE. (VendorCredit's flavor was subtler: it didn't delete the mapping, it silently fell through to its Step-3 CREATE on the empty read — same duplicate outcome, fixed the same way.) Re-resolve BEFORE mutating: **repoint the mapping in place** when a replacement binds (Project — it has an `update_by_id` sproc), or **when there is no repoint sproc** (Expense/Bill/BillCredit — their mapping repos have none, and no SQL migration was in scope) heal in place **only if a natural fingerprint re-binds the SAME mapped id** — `(reference_number, vendor)` for Expense (`ExpenseService.read_by_reference_number_and_vendor_public_id`), `(bill_number, vendor)` for Bill (`BillService.read_by_bill_number_and_vendor_public_id`), `(credit_number, vendor)` for BillCredit (`BillCreditService.read_by_credit_number_and_vendor_public_id`) — routing the number through `preserve_human_edited_ref` exactly like the happy path; on any other outcome record a critical `[qbo].[ReconciliationIssue]` (`orphaned_{purchase_expense,bill_bill,vendorcredit_billcredit}_mapping`, failure-isolated) and **RAISE, mutating nothing** — the caller's per-item handler skips it and the issue is the durable follow-up record. Never auto-recreate on an empty read. The same-id gate makes a wrong/duplicate row safe even when the fingerprint proc is not `TOP 1` (`id != mapping` → record+raise, never a wrong bind). NB the pull treats a raised `ValueError` as a *permanent skip* (watermark advances) — the in-tick fingerprint heal is the transient-recovery path, not "retry next tick". Applies to any new `sync_from_qbo_*`. Still OPEN (own units, need SQL / span connectors): a mapping-repoint sproc so a *different-id* fingerprint match can heal instead of raise, and lifting the heal + reconciliation-recorder shape into one shared QBO helper (three hand-copied recorders now — see TODO.md).
- **`qbo.*` IDs are NOT `dbo.*` IDs**: `qbo.Bill.Id`, `qbo.Purchase.Id`, `qbo.Invoice.Id` are staging-table internal PKs in a separate keyspace. The `qbo.BillLineItemBillLine` / `qbo.PurchaseLineExpenseLineItem` mapping tables only carry `dbo.BillLineItem.Id` / `dbo.ExpenseLineItem.Id`; to reach the dbo parent (`dbo.Bill.Id` / `dbo.Expense.Id`), hop through `dbo.BillLineItem.BillId`. **Never alias `qb.Id AS BillId`** in a `qbo.*` join — use `QboBillId`, etc. (See `feedback_qbo_dbo_id_keyspaces.md` — OHR2-GUEST-09 incident, 2026-04-26.)
- **MS outbox has no human-cancel window**: the `build.one.scheduler` Function App POSTs `/api/v1/admin/outbox/drain/ms` every 60s, so any row enqueued via `BillService.sync_to_excel_workbook()` / `ExpenseService.sync_to_excel_workbook()` / etc. is likely to be drained before you can review it. Audit IDs *before* calling enqueue — the only after-the-fact recovery is `clear_excel_range` row-by-row.
- **Invoice line item enrichment**: `enrich_line_items()` in `entities/invoice/business/enrichment.py` batch-fetches parent data per source type in one DB connection. Returns `vendor_name`, `parent_number`, `source_date`, `sub_cost_code_number/name`, `cost_code_number/name` (via `SubCostCode → CostCode` join), and `attachment_public_id`. Called by the packet generator in `entities/invoice/api/router.py`.
- **Invoice PDF packet**: `POST /api/v1/generate/invoice/{id}/packet` prepends two reportlab-generated TOC pages (basic: ONE ROW PER SOURCE bill/credit/expense at the sum of its lines billed on this invoice, "Multiple See Image" when they span sub cost codes, type→vendor; expanded: one row per line, cost_code→type→vendor with subtotals) before merging attachment PDFs; attachment pages follow the basic TOC's row order (first occurrence per shared Attachment). Uses `pypdf` + `reportlab` (both in requirements). TOC "Type" column is derived from `source_type` — no schema field needed.
- **Invoice QBO sync is pull-only** (re-enabled 2026-04-26). `scripts/sync_qbo_invoice.py` populates `qbo.Invoice` + `qbo.InvoiceLine` staging and creates local `dbo.Invoice` + `dbo.InvoiceLineItem` rows via `InvoiceInvoiceConnector.sync_from_qbo_invoice`. **The connector creates ILI rows with `SourceType='Manual'` and no source FK** — it does not back-resolve QBO LinkedTxn references to local Bills/Expenses. The packet generator and Excel reconciliation depend on the source FK, so any QBO-pulled invoice needs a fingerprint-matching step (`qbo.InvoiceLine` Description+Amount+ServiceDate → `qbo.BillLine` AND `qbo.PurchaseLine`) before generating its packet. Procedure documented in the InvoiceAgent playbook (auto-memory).
- **Invoice `complete_invoice` does NOT push to QBO** (deliberately disabled at `entities/invoice/business/service.py:406-409`). Local invoices created via `complete_invoice` mark source `IsBilled=True` locally but do not flip QBO `BillableStatus`. This means QBO continues to suggest already-locally-billed lines in its "Suggested Transactions" tray. Re-enable only when bidirectional QBO invoice sync is fully wired.
- **Invoice push DRY RUN (U-778d1) — read-only; nothing is written to QBO or the DB.** `POST /api/v1/qbo/invoice-push/dry-run` (a proposal: project, doc number, dates, BillLineItem/ExpenseLineItem/BillCreditLineItem ids, fee lines) returns per-line verdicts and the exact QBO invoice payload the push WOULD send — one invoice line per ReimburseCharge line, cost + markup, `LinkedTxn` with `TxnLineId` (the shape proven live on 2026-11-06); `POST .../compare` diffs that expected invoice against an existing QBO invoice of the SAME project (the shadow round). Gated by `INVOICES can_complete` + project access + env `QBO_INVOICE_PUSH` (`off` default → 404; `dry_run`/`on` enable). Code: `integrations/intuit/qbo/invoice_push/` (pure core model/eligibility/payload/canonical; read sprocs in `sql/dbo.invoice_push.sql`). Missing and other-project source lines get one opaque `source_line_unavailable` before any QBO read. The QBO transport still meters reads and may refresh the token. The WRITE path (U-778d2) is parked; design: `build.one.team/engineering/designs/u778d-invoice-push.md`.

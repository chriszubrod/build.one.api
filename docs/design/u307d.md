# U-307d design proposal — retire `cost_code_resolver`'s legacy fallback + Phase-6 guarded DROP of `qbo.Item` / `qbo.ItemCostCode` / `qbo.ItemSubCostCode`

**Status:** design proposal, no code/SQL changed, no prod mutation. Read-only investigation against current
code (2026-08-25, HEAD `028d2bdc`, api master) + live production database. **Decision in force:**
`project_qbo_trust_dbo_identity_alone` (umbrella memory, 2026-08-23) — trust `dbo.<Entity>.QboId`/`RealmId`
as the sole identity store; drop the redundant `qbo.*` mapping/staging second-stores. **Precedent:** U-307a
(built `cost_code_resolver.py`, forward + reverse, forward kept a legacy-hop fallback deliberately) → U-307b
(wired the 3 push consumers onto the reverse resolver, which was built fallback-free from day one) → U-307c
(retired the item connectors' + `QboItemService`'s `qbo.Item*` staging **writes**, deployed BATCH-4
2026-08-24 19:26:24Z) → U-316 (ROWVERSION structural hardening — board's own note: "Phase-6
(U-300c/U-307d/U-314) now unblocked"). **Sibling units, same session-day:** U-300c-design (Attachable's own
Phase-6 drop, `/em` Gate-2 **APPROVED** 2026-08-25) is the template this document follows section-for-section;
its one hard-won lesson — *"check each family's PUSH path for surviving mapping-table reads, not just
writes"* — is directly answered in §4.3 below. **Two-phase dispatch, Phase 1**
(`feedback_two_phase_dispatch_design_gated`): this document is the deliverable. No code written, no SQL
applied, no branch created.

**Headline finding.** Item/cost-code's remaining live reader is narrower and lower-risk than Attachable's: the
**push** direction (`resolve_qbo_item_ref`, dbo `SubCostCode.QboId` → QBO Item ref) was built fallback-free
from the start by U-307a's own Gate-1 call, so — unlike Attachable — there is **no** push-path legacy read to
repoint here (§4.3 proves this directly, not by assumption). The one deliberate dormant reader is the
**forward** resolver's legacy hop (`_legacy_resolve_sub_cost_code`/`_legacy_resolve_cost_code`), confirmed
**0%-hit today** across all 6 production call sites and **provably equivalent** at the one place it could
theoretically still matter (§4.2). A second, independent reader was found that has nothing to do with the
fallback at all: `integrations/intuit/qbo/item/api/router.py`'s 3 admin `GET` endpoints read `qbo.Item`
directly, with **zero** live callers (§4.4) — the same "dead-by-absence-of-caller, not dead-by-construction"
shape Attachable's push-path reader was NOT (that one fired on every real production call). Both readers close
in one small, mechanical, provably behavior-preserving prerequisite unit (§2, §8 Decision 3) before the
guarded DROP — the same two-step shape U-300c-design just established and got approved for.

## 1. Fallback-removal plan — the exact edit to `cost_code_resolver.py`

### 1.1 What exists today

`integrations/intuit/qbo/base/cost_code_resolver.py` (206 lines, U-307a) exposes 3 public functions:

- `resolve_dbo_sub_cost_code(qbo_item_ref_value, realm_id=None, *, sub_cost_code_service=None, qbo_item_repo=None, item_sub_cost_code_repo=None)` — dbo-native (`SubCostCodeService.read_by_qbo_identity`) first; on a miss, falls to `_legacy_resolve_sub_cost_code` (hops `qbo.Item → qbo.ItemSubCostCode`). Never raises — `None` on any miss at any hop.
- `resolve_dbo_cost_code_direct(qbo_item_ref_value, realm_id=None, *, cost_code_service=None, qbo_item_repo=None, item_cost_code_repo=None)` — same shape, `qbo.Item → qbo.ItemCostCode`.
- `resolve_qbo_item_ref(sub_cost_code_id, realm_id=None, *, sub_cost_code_service=None)` — **reverse**, already fallback-free (built that way by U-307a's own Gate-1 decision, wired by U-307b). Untouched by this unit.

Plus 2 private legacy-hop helpers (`_legacy_resolve_sub_cost_code` lines 166-184, `_legacy_resolve_cost_code`
lines 187-205), each lazily importing `QboItemRepository`, `ItemSubCostCodeRepository`/`ItemCostCodeRepository`
and defaulting to real instances when the optional repo params aren't supplied.

### 1.2 The edit

Delete `_legacy_resolve_sub_cost_code` and `_legacy_resolve_cost_code` outright. Collapse the two forward
functions to dbo-native-only, matching `resolve_qbo_item_ref`'s existing shape exactly:

```python
def resolve_dbo_sub_cost_code(
    qbo_item_ref_value: Optional[str],
    realm_id: Optional[str] = None,
    *,
    sub_cost_code_service: Optional[SubCostCodeService] = None,
) -> Optional[SubCostCode]:
    """dbo-native SubCostCode.QboId resolution for a QBO Item reference. ``None`` on no ref or no match --
    never raises. The legacy qbo.Item -> qbo.ItemSubCostCode staging hop this function used to fall back to
    was retired (U-307d) once dbo-native's live parity + the fallback's 0% hit rate made it dead weight --
    see docs/design/u307d.md."""
    if not qbo_item_ref_value:
        return None
    scc_service = sub_cost_code_service or SubCostCodeService()
    return scc_service.read_by_qbo_identity(qbo_item_ref_value, realm_id)
```

(and the CostCode-level twin, identically shaped). Drop the `qbo_item_repo`/`item_sub_cost_code_repo` /
`item_cost_code_repo` keyword params from both signatures — nothing left to inject. Rewrite the module
docstring's "Forward ... falling back to the legacy ... staging hop on a miss" paragraph to state the
dbo-native-only contract and point at this document for the retirement rationale, mirroring how U-315's own
docstring change documented the identical class of removal for Attachable.

## 2. Ordering constraint + unit sizing

**Hard sequence, non-negotiable:** the fallback *reads* `qbo.Item`/`qbo.ItemCostCode`/`qbo.ItemSubCostCode` —
dropping the tables before the fallback code stops referencing them breaks every fallback call
(`Invalid object name`) the instant a dbo-native miss occurs, even a 0%-today one. §4.4's router endpoints are
the same shape: they read `qbo.Item` unconditionally, unrelated to the fallback but equally blocking.
**(a) remove the fallback + close the router reader + delete the drift spec rows → ship → deploy → soak → (b)
drop the tables.** The DROP cannot precede step (a)'s deploy under any circumstance.

**One build unit (code) + a later, separate DROP unit — split, not combined.** This mirrors U-300c-design's own
Decision 1, approved by `/em` for Attachable earlier today: bundling a code change with an irreversible-in-spirit
schema DROP in one unit conflates two different risk classes this program's two-phase discipline exists to keep
apart. Proposed names, mirroring the `U-300c-prereq` / `U-300c` precedent exactly:

- **`U-307d-prereq`** — the code unit: §1's `cost_code_resolver.py` edit + the 5 caller cleanups (§1.3) + close
  the router reader (§4.4, recommend delete) + delete `identity_drift.py`'s `cost_code`/`sub_cost_code` spec
  rows (§4.5) + the 4+12 test-file kwarg updates. Small, mechanical, behavior-preserving per §1.4's live proof
  (the fallback's only two branches converge to the same answer on every real row today). P0-surface (QBO
  cost-code mapping), build directly, Codex `xhigh`.
- **Soak** — see §6.
- **`U-307d`** — the guarded DROP itself, per §3/§5.

## 3. Drop set + FK dependency order (live `sys.foreign_keys`, re-confirmed 2026-08-25)

```sql
SELECT fk.name, SCHEMA_NAME(tp.schema_id), tp.name, cp.name,
       SCHEMA_NAME(tr.schema_id), tr.name, cr.name,
       fk.delete_referential_action_desc, fk.update_referential_action_desc
FROM sys.foreign_keys fk
JOIN sys.tables tp ON fk.parent_object_id = tp.object_id
JOIN sys.tables tr ON fk.referenced_object_id = tr.object_id
JOIN sys.foreign_key_columns fkc ON fkc.constraint_object_id = fk.object_id
JOIN sys.columns cp ON cp.object_id = tp.object_id AND cp.column_id = fkc.parent_column_id
JOIN sys.columns cr ON cr.object_id = tr.object_id AND cr.column_id = fkc.referenced_column_id
WHERE tr.name IN ('Item','ItemCostCode','ItemSubCostCode') AND SCHEMA_NAME(tr.schema_id) = 'qbo';
```

**Result — exactly 2 edges, both outward from the two mapping tables, none inward to either mapping table:**

| FK | Parent (child) | Column | References | Column | Delete rule |
|---|---|---|---|---|---|
| `FK_ItemCostCode_QboItem` | `qbo.ItemCostCode` | `QboItemId` | `qbo.Item` | `Id` | NO_ACTION |
| `FK_ItemSubCostCode_QboItem` | `qbo.ItemSubCostCode` | `QboItemId` | `qbo.Item` | `Id` | NO_ACTION |

A second targeted query confirmed zero FKs reference `qbo.ItemCostCode` or `qbo.ItemSubCostCode` themselves —
matches `scripts/migrations/u225_qbo_mapping_fk_gaps.sql`'s original provenance and wave4-u307c.md's snapshot
without exception. **Drop order: `ItemCostCode` + `ItemSubCostCode` (children, either order relative to each
other) before `qbo.Item` (parent).** No line-junction sits beneath either mapping table (unlike Bill/Invoice's
header→line chains) — this is a flat, 2-level drop.

**Proposed guarded DROP SQL** (idempotent, matches the `IF OBJECT_ID`/`DROP PROCEDURE IF EXISTS` idiom U-286
and U-300c-design both used):

```sql
-- Phase-6 drop: qbo.ItemCostCode + qbo.ItemSubCostCode (children) before qbo.Item (parent).
-- Re-run §5's live re-verify query immediately before this — do not trust this
-- document's row counts, they decay the moment it's written.

IF OBJECT_ID('qbo.ItemCostCode', 'U') IS NOT NULL
BEGIN
    DROP TABLE [qbo].[ItemCostCode];

GO
```

`resolve_qbo_item_ref` call sites (`bill/connector/bill/business/service.py:965`,
`purchase/connector/expense/business/service.py:941`, `invoice/connector/invoice/business/service.py:1325`,

### 4.4 Zero-reader, bucket 3 — `integrations/intuit/qbo/item/api/router.py`'s admin `GET` endpoints (new finding, unrelated to the fallback)

Three RBAC-gated (`Modules.QBO_SYNC`) endpoints read `qbo.Item` directly, independent of
`cost_code_resolver.py`:

```python

@router.get("/get/qbo-items/realm/{realm_id}")    # → service.read_by_realm_id() → ReadQboItemsByRealmId
@router.get("/get/qbo-item/{qbo_id}")             # → service.read_by_qbo_id() → ReadQboItemByQboId
```

Grepped `build.one.web/src` for any caller of `qbo-items`/`qbo-item/` — **zero hits**. This is the same
"dead-by-absence-of-caller, not dead-by-construction" shape flagged for Attachable's `AttachableAttachment`
read-methods, but with an important difference in severity: Attachable's push-path reads **fired on every real
production call** (just happened to be behaviorally inert for that caller); these 3 GET routes are simply
**never called by anything today**. That makes them lower-risk (nothing breaks *today* either way) but they
would 500 (`Invalid object name` surfacing through the sproc) the moment the DROP lands if anyone — or any
future script — ever hits them. **Recommend: delete the 3 `GET` routes** as part of `U-307d-prereq` (§8
Decision 1) — there's no meaningful repoint target (a "list every raw QBO item ever pulled" admin debug view
has no dbo-native equivalent once the local cache is gone; QBO's own API is the source of truth going
forward). The `POST /sync/qbo-items` endpoint (line 17, calls `service.sync_from_qbo(...)`, the live pull
entrypoint) is **untouched** — it drives `ItemCostCodeConnector`/`ItemSubCostCodeConnector`'s dbo-native
writes and has no dependency on `qbo.Item` persisting (§4.1's transient-`_upsert_item` confirms it doesn't
even read-before-write anymore).

## 7. Rollback note

**No real data loss risk — these are provably redundant second-stores, not a primary record**, per
`project_qbo_trust_dbo_identity_alone`'s own framing (the one deliberately-irreversible call in the migration,
made by Chris). If a second store were ever needed again (not currently anticipated):

- `qbo.Item` would need re-population by re-pulling the Item catalog from the live QBO API — the pull machinery
  itself (`QboItemService.sync_from_qbo`, `POST /sync/qbo-items`) is untouched by this drop, only the local
  cache of it goes away; a full-realm re-pull reconstructs it (554 items today, small relative to Attachable's
  ~19k).
- `qbo.ItemCostCode`/`qbo.ItemSubCostCode` would rebuild trivially as `(CostCodeId/SubCostCodeId, QboItemId)`
  pairs derived directly from `dbo.CostCode.QboId`/`dbo.SubCostCode.QboId` joined back to whatever `qbo.Item`
  re-pull produced — no independent data of their own beyond that join (this is exactly why §1.4 could prove
  100% equivalence: the mapping tables never carried information dbo-native didn't already have, once U-289
  stamped it).
- The **schema** (table DDL, indexes, the 20 sprocs) is fully recoverable from git history even after the base
  SQL files are deleted (§5) — `git show <pre-drop-sha>:integrations/intuit/qbo/item/sql/qbo.item.sql`
  reconstructs it verbatim; it must be deliberately re-run rather than resurrectable by accident, which is
  exactly why §5 insists on deleting the files rather than editing them.

No BLOB, no financial figure, no user-facing record lives in any of the 3 tables — `dbo.CostCode`/
`dbo.SubCostCode` (the real records + their QBO identity) and QBO itself (the Item catalog) are the two real
sources of truth throughout; the 2 pre-existing dangling `ItemCostCode` orphans (§1.4) vanish for free on drop,
carrying no information not already dead today.

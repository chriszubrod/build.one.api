## 0. Why this unit exists, and why it's separate from the two already-shipped "-prereq" units

Both `u314.md` and `u307d.md` said the `identity_drift.py` registry-row fix should be **bundled into** their
respective prereq units rather than done as a shared cross-family unit (`u314.md:521-522`, `u307d.md:564-566`) —
directly reversing `wave4-u307c.md`'s own original recommendation for **one shared cleanup unit** spanning every
dbo-only family (`wave4-u307c.md:338-349`, Decision 4).

That bundling did not happen. `build.one.team/BOARD.md`'s BATCH-6 entry (2026-08-26) describes what actually
shipped in `U-314-prereq` (`35b59ff0` — "project write + vendor backfill dbo-only") and `U-307d-prereq`
(`7df2b6e8` — "cost-code resolver fallback retired") — neither description mentions `identity_drift.py`, and
reading the live file today (`integrations/intuit/qbo/base/identity_drift.py`, confirmed line-by-line below)
shows all 5 stale rows this doc addresses are **still present, unmodified**. The same BOARD entry explicitly
names the gap as still open: *"carrying the deferred `identity_drift.py` spec-row reconciliation (shared with
`backfill_qbo_active_mirror.py`)"* into the post-soak DROP dispatch. So U-325 is, in effect, `wave4-u307c.md`
Decision 4's original shared-cleanup unit — finally happening, three design docs later than first proposed, and
now also folding in `backfill_qbo_active_mirror.py` (which none of the three prior docs treated as needing more
than a one-line mention).

**This unit must ship (code merged) and deploy (prod container updated) before /em runs either the U-314 or the
U-307d DROP SQL** — both DROP migration files are already staged with that exact gate written into them
(`scripts/migrations/u314_drop_qbo_customer_project_vendor.sql`, `scripts/migrations/u307d_drop_qbo_item_cost_code_subcostcode.sql`,
both "STAGED, NOT APPLIED", both gated on "the separate identity_drift.py / backfill_qbo_active_mirror.py active-mirror
reconciliation unit has landed"). No SQL migration is required for U-325 itself — this is a Python-only change to
3 script files + 3 test files, no schema/sproc touched, no DB access pattern touched beyond removing dead SQL-building
paths.

All 4 import one of the two registries and iterate it; none catches the exception; all default to `--entity all`

**Post-drop failure, confirmed exact:** running any of the 4 with the default `--entity all` executes
`SELECT COUNT(*) FROM qbo.[VendorVendor]` (or `CustomerCustomer`/`CustomerProject`/`ItemCostCode`/`ItemSubCostCode`/
`Item`, depending on script) against a table that no longer exists → SQL Server error 208, surfaced as an uncaught
`pyodbc.ProgrammingError` — the script dies on the **first** affected entity in iteration order (`vendor` is index 0
in `REFERENCE_ENTITY_SPECS`, so `check_qbo_identity_drift_reference.py --entity all` / `backfill_qbo_identity_reference.py
--entity all` die immediately, before ever reaching `payment_term`/`address`/`bill_credit`; `check_qbo_identity_drift_headers.py
--entity all` reaches `project` at index 3, after `bill`/`expense`/`invoice` succeed). Narrowing `--entity` to one of
the 4 unaffected keys per script still works fine.

**Already broken today, independent of the drop.** Since the dbo columns for `project`/`vendor`/`customer`/
`cost_code`/`sub_cost_code` have been stamped with no corresponding mapping row present since each family's own
cutover, `classify_qbo_identity_drift` already misclassifies every such row as `orphan_dbo_value` — false-positive
noise on every drift-check run today, pre-existing and separate from the post-drop hard failure. This is the exact
gap both `u314.md` (§4.4) and `u307d.md` (§4.5) already documented and both recommended fixing the same way this
doc proposes.

**Confirmed CLI-only / unscheduled** — grepped `build.one.api` (script docstrings/logger names/TODO/SESSION_NOTES/
design-doc prose/test imports only, no cron context) and `build.one.scheduler` (zero hits at all, including its
~25 `@app.timer_trigger` registrations) for all 4 script names. No admin route references any of them either. A
failure can only be triggered by an operator (or an agent) running one of these 4 scripts by hand — it cannot fire
against a running system on its own.

## 3. `backfill_qbo_active_mirror.py` — narrower scope than the 4 drift scripts, but real

`scripts/backfill_qbo_active_mirror.py` filters `REFERENCE_ENTITY_SPECS` down to 3 keys (lines 36–37):

```python
_ACTIVE_MIRROR_KEYS = frozenset({"vendor", "payment_term", "sub_cost_code"})
SPECS_BY_KEY = {s.key: s for s in REFERENCE_ENTITY_SPECS if s.key in _ACTIVE_MIRROR_KEYS}
```

It does **not** build a `LEFT JOIN qbo.[{mapping_table}]` query like the drift scripts — it only ever uses
`.label`/`.staging_table` (its own comment says as much, line 31) to `UPDATE` a `QboActive` column directly on the
dbo table, joining to the **staging** table (not the mapping table):

| key | `.label` (dbo table) | `.staging_table` | Post-drop? |
|---|---|---|---|
| `vendor` | `Vendor` | `Vendor` | **Unaffected** — `qbo.Vendor` is explicitly out-of-scope for U-314's drop (`u314.md:126-127`: "Out of scope (raw STAGING mirrors — do NOT drop): `qbo.Customer`, `qbo.Vendor`"). Only `qbo.VendorVendor` (the mapping table) is dropped, which this script never touches. |
| `payment_term` | `PaymentTerm` | `Term` | **Unaffected** — `qbo.Term`/`qbo.TermPaymentTerm` are not part of either drop. |
| `sub_cost_code` | `SubCostCode` | **`Item`** | **BROKEN** — `qbo.Item` is dropped by U-307d. `INNER JOIN qbo.[Item] s ON ...` → `Invalid object name 'qbo.Item'`. |

There is no separate "mirror" table — the script `UPDATE`s `dbo.Vendor.QboActive` / `dbo.PaymentTerm.QboActive` /
`dbo.SubCostCode.QboActive` directly, comparing against the QBO-side `Active` flag on the respective staging table.

## 4. Investigation: does anything depend on the `sub_cost_code` active-mirror before retiring it?

The assignment asked to confirm this before recommending retirement. Findings (full repo grep, `.py`/`.sql`, api +
web + mcp):

- **`dbo.SubCostCode.QboActive` is not exclusively written by this backfill script.** Two independent, live,
  regularly-run writers already keep it current, and neither reads the table U-307d drops:
  - `integrations/intuit/qbo/item/connector/sub_cost_code/business/service.py:154-171` — the QBO item-sync
    connector calls `repo.set_qbo_identity(..., active=qbo_item.active)` on **every regular sync tick**. Since
    U-307c made the item pull **transient** (`wave4-u307c.md:213-224` — `QboItemService._upsert_item` now builds an
    in-memory-only `QboItem` straight from the QBO API response, no DB round-trip), `qbo_item.active` comes from the
    live API response, **not** from a `qbo.Item` table read — this write path is entirely unaffected by dropping
    `qbo.Item`.
  - `entities/sub_cost_code/sql/dbo.subcostcode.sql:480` — `SetSubCostCodeQboIdentity`'s `CASE WHEN @Active IS NOT NULL
    THEN @Active ELSE [QboActive] END` preserves/updates the column on every stamp, independent of this script. (Not
    `UpsertSubCostCode`, a separate sproc in the same file that only touches Number/Description/Aliases — corrected
    per §10's independent verification pass.)
- **The `sub_cost_code` active-mirror comparison has already been reading stale data since U-307c shipped** (BATCH-4)
  — `qbo.Item` stopped receiving writes at that point (`u307d.md:290-307` confirms zero-write since BATCH-4), so this
  script's `sub_cost_code` branch has been comparing `dbo.SubCostCode.QboActive` against a **frozen snapshot**, not
  live QBO state, for as long as U-307c has been deployed. Its diagnostic value for this one key was already
  degraded before this unit; the drop just turns "silently stale" into "hard error."
- **No application logic reads/gates on `qbo_active` anywhere.** `grep -rn "\.qbo_active\b"` across every `.py` in
  `build.one.api` → zero hits (the field is read off the row into the dataclass and serialized in `to_dict()`, but
  nothing branches on it). `build.one.web/src` and `build.one.mcp` → zero hits each; the frontend doesn't render it
  despite it being present in the API JSON payload.
- Same pattern (independent live writer, staging table not dropped) holds for `vendor` and `payment_term` — only
  `sub_cost_code` loses its staging source.

**Conclusion: retiring the `sub_cost_code` active-mirror entity is safe.** It removes a diagnostic/catch-up tool
whose one source of truth is being dropped and which has already been degraded (comparing against frozen data)
since U-307c — not a live data-currency dependency. This is flagged as **Decision A** in §8, not treated as settled
unilaterally, since it's the one substantive behavior change in this unit (everything else is dead-registry-row
cleanup).

## 5. The decoupling problem, and why §4's retirement makes it worse if left coupled

`backfill_qbo_active_mirror.py`'s `SPECS_BY_KEY` is a **filter over `REFERENCE_ENTITY_SPECS`**, not its own list.
§7's registry fix deletes the `vendor` row from `REFERENCE_ENTITY_SPECS` (needed so the drift scripts stop querying
the dropped `VendorVendor` mapping table). But `vendor`'s **active-mirror** entry doesn't need to go anywhere — its
staging table (`qbo.Vendor`) survives untouched, and §4 already showed it's fully functional post-drop. If the
`vendor` row is simply deleted from `REFERENCE_ENTITY_SPECS` and the active-mirror script is left as-is, `SPECS_BY_KEY`
silently loses `vendor` too — not because vendor's active-mirror broke, but because it was never supposed to be
coupled to the drift-registry's row set in the first place.

Today, one test happens to catch this specific case as a **loud failure**, not a silent regression:
`tests/test_backfill_qbo_active_mirror.py::test_specs_filtered_to_exactly_the_three_active_mirror_entities` pins
`SPECS_BY_KEY.keys() == {"vendor", "payment_term", "sub_cost_code"}`. But relying on that pin catching every future
cross-family registry edit is exactly the kind of implicit coupling this program has been tripping over unit after
unit (the whole reason `wave4-u307c.md`'s Decision 4 exists). **Recommendation (Decision B, §8): decouple
`backfill_qbo_active_mirror.py` from `REFERENCE_ENTITY_SPECS` entirely** — give it its own minimal 2-row spec list
for `{vendor, payment_term}` (`sub_cost_code` retired per Decision A), since the script only ever reads `.label`/
`.staging_table`:

```python
@dataclass(frozen=True)
class ActiveMirrorSpec:
    key: str
    label: str
    staging_table: str

_ACTIVE_MIRROR_SPECS: tuple[ActiveMirrorSpec, ...] = (
    ActiveMirrorSpec("vendor", "Vendor", "Vendor"),
    ActiveMirrorSpec("payment_term", "PaymentTerm", "Term"),
)
SPECS_BY_KEY = {s.key: s for s in _ACTIVE_MIRROR_SPECS}
```

This removes the script's `from integrations.intuit.qbo.base.identity_drift import FlatEntitySpec,
REFERENCE_ENTITY_SPECS` import entirely — it becomes self-contained, and future edits to `REFERENCE_ENTITY_SPECS`
(which exists to serve the drift-check scripts, a different concern) can no longer silently change what this
script covers.

## 8. Decisions needing /em sign-off

### Decision A — retire the `sub_cost_code` active-mirror entity outright (recommended)
§4's investigation found no live dependency: the connector + `UpsertSubCostCode` sproc already keep
`dbo.SubCostCode.QboActive` current independently of this script, and the script's own comparison has been reading
a frozen `qbo.Item` snapshot since U-307c (before this unit even exists). **Recommendation: retire, don't
telemetry-first** — same reasoning `u307d.md`'s own Decision 3 used for the resolver fallback (exhaustive proof,
not a sampling argument). Alternative not recommended: keep a `sub_cost_code` active-mirror pointed at
`dbo.SubCostCode` alone with no QBO-side comparison — pointless, since the whole point of this script is comparing
against QBO's live `Active` flag, and there is no surviving QBO-side source for it once `qbo.Item` is dropped.

### Decision B — decouple `{vendor, payment_term}` from `REFERENCE_ENTITY_SPECS` into a standalone spec list
Recommended in §5 to stop this exact class of cross-file silent narrowing from recurring the next time
`REFERENCE_ENTITY_SPECS` changes for drift-check reasons unrelated to the active-mirror. Alternative not
recommended: leave the filter-over-shared-registry pattern and rely on
`test_specs_filtered_to_exactly_the_three_active_mirror_entities`-style pinning tests to catch future drift —
works today only because someone already wrote that exact test; it's not a structural guarantee.

### Decision C — confirm the exact 5-row removal list and resulting registry shapes
`HEADER_ENTITY_SPECS`: `bill`, `expense`, `invoice`, `company` (4). `REFERENCE_ENTITY_SPECS`: `payment_term`,
`address`, `bill_credit` (3). This is the one edit every other consumer in §6 depends on being exactly these 5 keys
— confirm before Phase 2 build starts.

### Decision D — this unit ships as ONE combined unit (registries + both scripts + all 3 test files), not split
Matches the file-family logic `u300c.md`/`u314.md`/`u307d.md` each used to justify bundling their own family's
row into their own prereq unit (small, same-file-family, no design work) — except here it's finally the one shared
unit `wave4-u307c.md` originally asked for, covering both families' stale rows plus the active-mirror decoupling in
one pass, since it all touches the same shared primitive and its one CLI-script dependent chain.

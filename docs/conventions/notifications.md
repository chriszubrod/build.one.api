- **Review-submit notifications (May 2026, forward-of-original; Expense added later — see end of bullet)**: First-time draft Bill creation auto-fires an email notification via `entities/review/business/notification_service.py`. The notification is a **draft FORWARD of the original vendor email** (`Bill.SourceEmailMessageId → EmailMessage.GraphMessageId → me/messages/{id}/createForward`) so reviewer replies stay in the same MS Graph conversation thread as the source. Recipients resolved by `dbo.ResolveReviewRecipientsByBillId` walking Bill → BillLineItem → Project → UserProject (filtered to `Role.Name='Project Manager'` / `'Owner'`) → User → Contact. **TO** = all PMs, **CC** = all Owners, **BCC** = `Settings.invoice_inbox_email` (always). Submitter excluded. Subject is auto-prefixed by Graph (`FW: <original>`). HTML preamble is prepended to the forwarded body via 2-step POST createForward + PATCH (PATCH is content-type-aware: `\n` → `<br>` for plain-text source emails; `<body>`-tag injection for HTML source emails). Preamble opens with a slash-joined firstname greeting (`Cassidy/Zach,`) when PMs are resolved. PDF attachment inherited from the source. Channel: MS outbox `Kind='send_mail'` → `create_forward_draft` (mode=draft, default) or `forward_message` (mode=send) by `REVIEW_NOTIFICATION_MODE` env var. Failure-isolated — never rolls back Bill or Review row. **Bills without `SourceEmailMessageId`** (manual web-UI creation) are silently skipped today; synth-email fallback design captured in TODO.md. v1 limits: see `project_review_notifications.md` memory + TODO.md "Review-submit notifications follow-ups". Runbook: `docs/runbooks/review-notification-failed.md`. **Reviewer assignment requires populating `UserProject.RoleId`**; no React UI yet, do via SQL. **Expense** has its own path (`ReviewNotificationService.enqueue_for_expense`, fired from `ReviewService.create` on the initial submit only): recipients via `ResolveReviewRecipientsByExpenseId`, an HTML-composed `send_mail` (no source email to forward) with the receipt attached by `blob_url` reference (never downloaded on the request path), then an auto-advance to `in_review` and `ExpenseService.enqueue_coding_recode_on_submit` (U-486 C2) — all DB-only; ~20–30 sequential connections, no inline external HTTP.

## Reviewer reply ingestion (U-797c3)

- **What is copied:** inbox messages whose Graph `conversationId` is an open review thread, stored as `dbo.EmailMessage` rows with status `reviewer_reply` (no agent claims them). Insert path is `MailboxPollService._ingest_messages`, idempotent on InternetMessageId + Folder. Attachments are not downloaded.
- **Open-conversation rule:** `dbo.ReadOpenReviewReplyConversations` (45-day window on `ReviewNotification.CreatedDatetime`). A thread is open when its notification has a target that still awaits review: a bill in `submitted` or `in_review`, an expense in `submitted` or `in_review` (not `IsDraft`, which is computed as "not completed" and would also match approved and declined expenses), or a contract labor row in `pending_review` or `submitted`. Matching is exact and case-sensitive (BIN). Other mail is never stored.
- **Timers:** `review_reply_ingest` every 10 min (lookback 3 h, `POST /api/v1/admin/review-replies/ingest`); `review_reply_catch_up` daily 07:05 UTC (`POST /api/v1/admin/review-replies/catch-up`), under the same `ms_app_lock` as the ingest, so the two never overlap.
- **Flag:** `REVIEW_REPLY_INGEST_ENABLED` (default off). Off, paused (`PAUSE_EMAIL_POLL`), or no `invoice_inbox_email` means no DB or Graph call.
- **Nothing is applied.** Copied replies are stored for review. This unit never changes a bill, expense, or contract labor row.
- **Catch-up budget:** `catch_up` stops starting new conversations after 45 s and reports `checked` and `remaining`. The order is a shuffle seeded by the UTC date ordinal (stable within a day, different each day). Coverage is probabilistic: the 10-minute ingest is the primary path and this walk is the backstop. Each conversation is listed with its own filter and inserted through the same path as the ingest; `copy_review_thread_replies` is not used (it reads back stored rows and returns totals).
- **Watermark hazard:** copied replies advance `MAX(ReceivedDatetime)`, the watermark of the dormant forward poll (`/admin/email/poll`). Reviving that poll would skip earlier inbox mail unless `ReadMaxReceivedDatetimeByMailbox` first excludes `ProcessingStatus='reviewer_reply'`.

## Record, composer and the payload key (U-797c2a)

- **Shared pieces:** `entities/review/business/review_email_composer.py` owns the `[Review] ` subject prefix, recipient mapping, the archive BCC (Bill/Expense `Invoice Inbox (archive)`, Contract Labor no name), the slash-joined greeting (Contract Labor dedupes first names, Bill/Expense do not), the reviewer ask wording, and record-then-send. Subject bodies, line items and recipient resolution stay in each service.
- **Record before the email:** Bill and Expense write `dbo.ReviewNotification` before `enqueue_send_mail`; Contract Labor's crew claim is already written first. The record id goes in the payload as `review_notification_id`, written only when a record exists. A record failure enqueues the identical email without the key. A refused or raised enqueue releases the record. The outbox id is attached after the enqueue (audit only).
- **Worker stamp:** payload key present means `StampReviewNotificationById`. Otherwise Bill, Expense or ContractLabor rows fall back to `StampReviewNotificationFromOutbox` (rows enqueued before this deploy). Any other mail makes no DB call. The stamp never fails or retries the send_mail row.
- **Golden rule:** `tests/test_u797c2a_goldens.py` and the U-754 characterization pin the enqueue call. Do not regenerate them. The payload key is the one deliberate addition.

## Contract Labor crew email: suggestions, wait and snapshot (U-797b1)

- **Table (flag on):** one table per (project, date): Worker, Hours, Is Billable, Is Overhead, Notes/Description, Suggested code, Note. The Suggested code cell shows `NN.NN Name` only for a completed row whose DecisionSource is history or model, with a SubCostCodeId, not holding. A split shows `(split?)` with the candidates in Note. Otherwise `no suggestion`.
- **Ask:** `Reply "Approved" to apply the suggested codes, or reply with a sub cost code to apply it to the whole crew.` The reply path (bare Approved) is U-797b2, not this unit.
- **Own flag (fix round 1):** every behaviour below rides `CL_SUGGESTIONS_IN_REVIEW_ENABLED` (Settings `cl_suggestions_in_review_enabled`, default off, read strictly: only a real True or "true"). Flag off is trunk's email byte for byte: the paragraph layout with Is Billable / Is Overhead, the trunk ask, no snapshot, no wait. `CL_CODING_SHADOW_ENABLED` (already on in prod) only produces the rows.
- **Marker (round 2):** a held day is marked in `dbo.ContractLaborReviewHold` (only with the suggestions flag on). The sweep and the completion re-fire act only on marked days. The marker is deleted on claim success. The fifth fire that does not delete it gives up (`GaveUpDatetime`) and logs ids only.
- **Wait:** with the suggestions flag on, a (project, date) email is held while any suggestion row for that project is `pending` and the crew's latest submit (ContractLabor.ModifiedDatetime) is under `CL_SUGGESTION_WAIT_MINUTES` (30). Flag off, or no rows, means no wait. Once a row settles, the shadow tick re-fires the drafts for the marked day. Its sweep releases a marked hold after the timeout, on every tick whatever the flags. A pending row past the timeout goes out as `suggestion pending when sent`.
- **Order:** `ReviewService.create` enqueues the shadow rows before `enqueue_drafts`, so the wait sees them.
- **Snapshot:** the claim writes one `ReviewNotificationTarget` row per crew member with `SuggestedSubCostCodeId`, `SuggestionId`, `SuggestionSource`, `SuggestionMaySplit` (as shown) and `LinesFingerprint` (`cl_lines_fingerprint`, SHA-256 of the sorted `lineItemId:hours` pairs). Bill, Expense and BillCredit targets leave these NULL. Reader: `ReviewNotificationRecordService.read_crew_snapshots`.
- **Goldens unchanged (fix round 1):** `tests/test_u797c2a_goldens.py` is back to trunk. The flag-off email is trunk's, so the CL goldens did not change. The flag-on table is pinned by `tests/test_u797b1_email.py`.
